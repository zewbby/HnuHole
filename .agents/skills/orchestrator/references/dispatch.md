# 五项派单协议

总指挥在迭代执行循环中使用此契约。每次派单只包含以下五项，详细范围与接口约定指向同一份任务文档。

首次派单、中断恢复或规则／任务契约版本变化时做轻量核对，不增加派单字段；同一 Session 使用同一版本持续执行时不重复确认：

- 确认能创建或复用执行 Session、读取结果并传递消息。必要能力不足时说明限制，可继续不依赖该能力的已授权工作；不声称已派工，也不擅自把多 Session 交付改为单 Session。
- 固定本轮规则版本和任务契约版本，派单前核对执行 Worktree 的 `AGENTS.md`、`CONTRIBUTING.md` 与规则版本一致，任务文档的指定版本在该环境可读。执行 Session 接单后读取并回报所用版本；不一致或规则是否生效尚不明确时，先解决阻碍再执行受影响工作。只在 Git 中读得到新提交，不代表旧 Worktree 或既有 Session 已采用新规则。旧 Worktree 可在保留已有改动的前提下定向引入规则变更，不必同步全部产品代码。
- 入口 Session 默认负责汇总权威任务状态，执行 Session 回报结果，不并行改写任务文档。恢复前核对已有 Session 回报、分支与 Worktree 的提交、未提交及未跟踪改动；Session 暂不可读记为未知，不据此认定没有进展或重派重叠工作。

| 项目 | 内容 |
| --- | --- |
| 任务 ID | 稳定编号，便于追踪依赖和证据 |
| 目标 | 本轮要形成的可观察行为或集成结果 |
| 任务文档 | `docs/tasks/<ID>.md@<提交>`（或带版本标识的可访问固定快照）及相关章节；注明本轮规则版本 |
| 依赖 | 上游接口、分支、资源与交付顺序；没有则写“无” |
| 交付条件 | 可集成的源码版本、应通过的聚焦验证、证据和已知缺口 |

状态维护人修改目标、范围、接口、影响执行的依赖或验收标准时，固定新的契约提交／快照，说明变化及受影响任务并通知对应执行 Session；执行者确认新版本后继续受影响工作。规则变化也通知受影响 Session 重新读取并确认。纯进度或证据更新可继续写入同一任务文档，不改变已确认的任务契约，无需重新确认。

执行 Session 负责选择具体实现与命令，保留自己的分支和 Worktree。回报时给出当前状态、提交或差异位置、实际运行的验证及结果、阻碍与所需决策；不重复整份项目背景。总指挥接收后及时核对接口并集成，或将阻碍交给相应负责人解决。

一轮排查要有明确假设、动作和结果；只有能缩小原因范围或改变下一步决策的信息才算新证据。同一问题连续两轮没有新证据时，暂停该项无依据重跑，由总指挥调整诊断；仅在需要产品、授权或资源取舍时升级给用户。

示例：

```text
任务 ID：FEED-02
目标：让推荐结果通过现有首页接口返回并显示。
任务文档：docs/tasks/FEED-02.md@<契约提交>；规则版本：<规则提交>
依赖：FEED-01 的响应契约；先接入最小真实链路。
交付条件：独立分支可集成；服务端与客户端聚焦测试及被测提交记录完整。
```
