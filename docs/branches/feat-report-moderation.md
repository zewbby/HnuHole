## 目标与本次包含

交付“用户举报→网页审核→处理结果／申诉”的可追溯链路，先针对已经存在的帖子，再接任务1的评论。
所属B11与B08最小系统通知；作者删帖和已有处罚基础已存在，核对后复用，不能重复实现整套认证／账号系统。

1. App帖子举报入口、既定六类原因、说明／材料提交、原请求结果核对、失败保留与重试、提交后的进度和结果。
   举报成功不等于举报成立；相同违规事实合并处理，目标删除按既定规则终结未完案件。
2. 服务端举报／案件／证据快照／处理动作／审计模型、迁移、最小权限与API。处理和内容生命周期在权威事务裁决，
   多人处理、重复请求、重复举报和删除竞争不能重复处罚或复活内容。
3. 电脑网页管理端的最小工作台：登录／权限、案件列表／详情、授权证据、下架、限时禁言、封禁／解除及必要操作记录。
   角色保持已定边界：审核员负责其允许的下架／资料重置／限时禁言，管理员才可封禁、解封和管理权限。
   管理端展示六位平台编号及允许的最小字段，不下发邮箱、资格槽位、内部账号映射或其他面具列表。
4. App最小系统通知列表、详情、已读与资源跳转，承载举报进度、结果、账号处罚及任务1的评论发送失败入口。
   账号级通知与身份级通知分别隔离；打开列表不批量已读，解决评论失败任务后才移除对应入口。
5. 已确认的处罚通知／申诉入口与对应处理结果，按既定权限、次数和逆向恢复规则实现本次处罚的必要闭环。
   真正未确定的授权、编号隐私或证据期限细节，提出具体场景与方案，不能用“后台可看全部数据”代替设计。
6. 产品API/真实SQL/权限/网页与移动端测试及CI；普通用户不能调用管理动作，管理员操作留可核对的审计事实。

## 任务1依赖与本任务提供的接口

任务1 `codex/feat/comments-replies` 拥有评论、评论图片、作者删除、评论发送任务与失败重试核心。
本任务拥有系统通知基础和管理操作；先提交通知接口契约，包含事件／任务唯一标识、身份或账号范围、目标引用、状态和允许路由。
评论失败保留内容／重试／放弃由任务1提供，通知层不复制发布状态机、不自行变更发送身份或冒充未知结果已失败。
本地失败入口与服务端通知的来源须标明，不能为了展示通知伪造服务端已经受理。
先做已有帖子的举报审核；评论目标适配等任务1固定接口可用后接入。缺依赖时保持明确未集成，不做绕过鉴权的占位实现。
先通过独立可审查PR交付通知基础和帖子举报，评论目标仍明确未接入；其合入后任务1从main接入并交付评论，
本任务再接评论举报和失败通知完成集成。可分阶段PR，不让两方互相合并整条未完成分支，避免环形依赖。

HTTP处理器使用相应独立文件。移动端放 `apps/mobile/lib/src/reports/`、`system_notifications/`，管理端放 `apps/admin/`。

0015须可应用于尚无评论表的main；评论目标后续经有类型适配器检查，保持资源归属和生命周期完整性。
若确需新增评论专用DDL，等任务1的0016实际合入后按实时编号增加后继迁移，不预占或覆盖其他任务文件。
开工与送审时核对编号占用；不允许缺失／乱序迁移，不改已合入迁移来掩盖冲突。
共享路由／权限／账号生命周期只做必要接线，先核对归属，保持C/V分离和现有Gate规则。
