# 隐私认证与邮箱—账号不可关联

状态：**superseded（2026-09-26）**。本 ADR 保留为历史决策；用户已改为“每次注册验证校邮，日常用户名＋密码登录，同一精确邮箱地址同时最多一个有效账号”。当前认证架构以[认证与隐私架构决策](../design/auth-privacy-architecture-decision.md)为准。下文邮箱唯一登录、稳定匿名凭证重复登录及无条件的不可关联结论不再作为实施依据；现方案有两方共享的随机槽位，串通或共同泄漏时可连接邮箱与账号。

## 背景

项目需要同时满足以下事实：

- 用户只输入校园邮箱并接收验证码，不设置登录密码，也不提供平台人工恢复入口。
- 首次验证后要能回到同一有效账号，保持本机草稿、会话替代、注销缓冲和账号内容归属。
- 管理端、社区业务和普通开发人员不能知道某个具体验证邮箱对应哪个具体账号。
- 现有“验证服务保存邮箱匹配标记”的方案仍保留邮箱—账号关联，不能直接作为最终隐私方案。

如果一个组织同时控制邮箱验证、社区服务、生产数据库、日志和部署权限，它可以把两边数据合并；单纯不存明文邮箱、使用普通哈希或增加后台权限都不能消除这条关联。

## 决策

### 1. 分离信任主体

- **邮箱验证方**处理完整收件地址、验证码发送和邮箱控制权确认，但不得接收社区账号编号、帖子归属或公开身份。
- **社区服务方**处理稳定匿名凭证、账号编号、会话和社区数据，但不得接收完整邮箱或可反推出邮箱的验证材料。
- 两方由不同组织或法律主体控制。密钥、日志、请求关联标识、备份和部署权限不得由同一人员单独掌握。
- 管理端只处理平台编号和社区业务结果，不开放邮箱、稳定匿名凭证或邮箱反查接口。

### 2. 使用稳定匿名凭证

- 用户完成邮箱验证码后，由隐私保护协议产生稳定匿名凭证。候选实现包括盲签名、门限 OPRF 或经安全评审的等效协议；具体算法、参数、密钥轮换和协议库尚未选定。
- 稳定匿名凭证不作为旧设备长期保存的恢复秘密；每次重新完成邮箱验证后，应通过隐私协议重新取得同一 Hnuhole 作用域内的稳定匿名标识。换机、卸载或清除本地数据后仍只依赖邮箱验证码恢复原有效账号。
- 稳定匿名标识必须绑定 Hnuhole 的服务作用域；同一验证邮箱在其他应用或社区中必须得到不同、不可直接关联的匿名标识。
- 协议密钥可以轮换，但轮换不得改变用户在 Hnuhole 内的逻辑匿名主体；具体迁移或版本过渡方式由协议实现和安全评审确定。
- 验证方看到邮箱和验证码流程，但看不到该凭证最终对应的社区账号。
- 社区服务看到凭证与内部账号映射，但不能从凭证直接得到邮箱。
- 社区服务使用该凭证返回同一有效账号；正式注销后按账号生命周期创建新账号。禁言在七天注销缓冲期间继续生效，但正式注销完成时随旧账号终止，不延续到新账号；封禁仍生效时禁止申请注销，缓冲期内新封禁会取消注销申请。
- 稳定匿名凭证不是邮箱原文、普通无密钥邮箱哈希、会话令牌或公开平台编号。

### 3. 登录与恢复边界

- 邮箱控制权是唯一登录凭证。用户失去邮箱访问权时，平台不提供人工恢复、管理员解锁或开发者代办恢复。
- 验证服务暂时不可用时，登录失败并允许稍后重试，不回退到人工查询或备用登录入口。
- 对格式、域名均合规的验证码申请，客户端始终收到相同的受理状态和通用提示“如果可以发送，验证码将到达邮箱”，不区分新邮箱与已注册邮箱。只有邮箱验证码验证成功后，社区侧才创建新账号或恢复已有账号。
- 任何接口、导出、日志、错误监控、队列和备份都不得形成可由单一主体合并的邮箱—账号记录。

## 威胁模型边界

本决策保证：

- 任一单独的验证方人员、社区服务人员、管理人员、数据库只读人员或普通开发人员，不能取得具体邮箱与具体账号的对应关系。
- 邮件服务商可以处理收件地址，但不应获得该地址对应的社区账号。

本决策不保证：

- 两个独立服务主动交换数据、共享日志或共同持有全部密钥时仍不可关联。
- 用户邮箱服务商、用户设备本身或完全控制客户端、全部生产服务和发布流程的恶意人员无法获知信息。
- 通过 IP、设备、时间、行为或内容推断现实身份；该目标另行建模。

## 后果

### 正面后果

- 社区业务可以持续使用内部账号和平台编号，不把邮箱带入帖子、评论、身份或管理接口。
- 用户仍能用邮箱验证码回到同一账号，不需要记住密码或平台编号。
- 任何单一内部主体都缺少完成邮箱—账号关联所需的另一半信息。

### 代价与风险

- 必须运营或委托两个真正独立的服务主体，增加部署、合同、可用性和故障排查成本。
- 协议选择、实现、密钥托管、时间关联防护和日志清理需要独立安全评审；在完成前不得宣称已实现不可关联。
- 两方串通、旁路日志、备份、邮件队列和客户端泄露仍可能恢复关联，必须作为验收和事件响应场景测试。
- 没有邮箱访问权时无法恢复账号；这是隐私边界的直接结果。

## 被否决的替代方案

- 在单一验证服务中保存 HMAC、普通哈希或加密邮箱到账号的映射：仍由掌握服务、密钥或运行内存的主体完成关联。
- 只在管理后台隐藏邮箱：不解决日志、备份、邮件队列和高权限运行时访问。
- 完全不保存稳定匿名凭证：无法保证重复登录回到同一有效账号，也无法正确处理注销缓冲期内的账号生命周期。
- 提供管理员人工恢复：建立可被内部人员滥用的邮箱—账号关联入口。

## 验收方向

- 独立验证方、社区服务方和管理端的数据库、API、导出、日志、错误监控、队列、备份中不存在可由单一主体合并的邮箱—账号记录。
- 验证方无法仅凭自身数据得到社区账号；社区服务方无法仅凭自身数据得到邮箱。
- 同一邮箱的重复验证回到同一有效账号；换机或重装后重新验证仍取得同一 Hnuhole 匿名主体；同一邮箱在其他服务得到不同匿名标识；密钥轮换不改变逻辑主体；正式注销后按规则创建新账号，旧禁言不延续，封禁期间不能注销，注销缓冲期内新封禁会取消申请。
- 认证请求的幂等键、时间戳、请求编号和故障排查材料不能成为跨服务可 join 的关联键。
- **已确认的客户端抗枚举规则及待评审侧信道**：对格式和域名合规的申请，新旧邮箱返回相同受理状态和通用提示“如果可以发送，验证码将到达邮箱”；只有验证码验证成功后才创建或恢复账号。该规则不承诺实际投递、响应时延或限流表现完全相同；这些可观察侧信道的风险与验收标准仍待独立安全评审。
- 对服务串通、数据库只读、密钥泄露、日志恢复、客户端篡改和邮件供应商旁路记录分别进行演练，并明确哪些属于本 ADR 的保证范围。
