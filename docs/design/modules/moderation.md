# 内容管理与社区治理

更新：2026-10-09。当前规则只在本模块维护。

- 状态：六位顺序平台编号、账号列表与搜索、违规记录、禁言时长及范围、封禁后申诉路径已确认；后台只显示平台编号，邮箱和内部匹配标记不可见。具体界面、审计及异常流程待细化。

## 范围

本人内容编辑删除、举报及管理员处理。主题屏蔽不在首版，见[标签模块 TAG-BLOCK-DEFERRED-01](tags.md)。

## 已确认范围

- 用户可以编辑或删除自己的帖子；评论及楼中楼只支持删除，不支持编辑。
- 首版管理后台采用电脑网页；手机 App 提供用户侧举报、处理通知和申诉，不加入管理工作台。
- 审核员可见范围、删除内容/限时禁言/封禁账号和申诉入口已确认；具体审核流程、角色授权及后台页面仍在设计阶段。

## 已确认规则

### EDIT-POST-01：发布后可随时编辑

- 原发表身份仍存在且帖子未被下架时，可以随时编辑本人帖子标题、正文、图片及自定义标签，保存后显示“已编辑”；所属通道不变。已下架帖子按 MOD-TAKEDOWN-01，不提供修改后重新审核。身份已删除的旧帖从其他入口可删不可编辑，见[身份模块 MASK-ARCHIVE-01](identity.md)；自定义标签选填、最多三个，见[标签模块](tags.md)。
- 编辑保留原发言身份、点赞和评论，不重新发布成另一条帖子；编辑也不能将内容改挂到另一身份。
- 编辑后的内容仍遵守[发帖模块](post-composer.md)的标题、内容与图片限制。
- 保存修改失败时，读者继续看到修改前版本，作者本次修改保留并可重试；保存成功后才整体替换，不向读者展示部分更新的内容。
- 发布时间旁显示“已编辑”，点击查看最后修改时间；普通读者只看当前内容，不开放历史版本列表。举报提交时保存的证据按 REPORT-EVIDENCE-01 处理。大通道不可换，评论不可编辑；首版不设中间分类及其屏蔽联动，按[标签 TAG-DIRECTION-02 / TAG-BLOCK-DEFERRED-01](tags.md)执行。
- 读者发表评论不因帖子被编辑而要求核对或再次确认；第六轮已取消该功能，见[评论模块 COMMENT-POST-UPDATED-01](comments.md)。

### EDIT-POST-DRAFT-01：退出旧帖编辑不保留修改

- 编辑已发布帖子但未点击保存就退出时，本次修改直接丢弃，不弹确认提示，原帖继续展示上次已保存的公开版本。
- 再次进入编辑时始终从当前公开版本开始；只有明确保存且保存成功后才更新公开内容。


### EDIT-COMMENT-01：评论不可编辑

- 首版主评论和楼中楼回复发布后不可编辑；需要修改时可删除后重新发送。
- 删除主评论会移除整楼，删除楼中楼回复仅移除本条，范围按 DELETE-COMMENT-01；重新发送是新评论，不恢复已删除内容或改变保留回复的原目标关系。


### DELETE-COMMENT-01：主评论删除整楼，楼中楼仅删除本条

- 第七轮按评论层级区分：删除一条主评论时，该主评论及其所属楼中楼回复一起删除；删除楼中楼中的一条回复时，只删除本条，其他人回复它的内容保持不变，不沿回复关系继续删除。
- 例如甲发主评论，乙回复甲、丙回复乙、丁回复甲：删除乙只移除乙，甲、丙、丁均保留；删除主评论甲则整楼一起移除。这里依据被删内容的层级，不因发言者是整篇帖子的作者就获得额外删他人评论的权限。
- 被实际删除的评论不在原位置保留“评论已删除”占位、头像昵称、赞数或操作入口。保留下来的回复继续显示其本身内容及“回复 xxx”，不展示引用原文或删除引用占位，按[COMMENT-QUOTE-01](comments.md)执行。
- 评论总数按本次实际删除数量扣除；参与讨论人数按剩余有效发言重算。已提交举报仅在它所指向的内容实际删除时按 REPORT-TARGET-01 终结；被保留的回复不因回复目标删除就视为自身删除。
- 第八轮用户明确删除主评论不用提示：点击删除直接执行整楼删除，不弹确认框或“整楼回复将一起删除”的影响提示。此决定关闭第七轮遗留的主评论删除确认问题；不据此取消身份、草稿或聊天删除已明确的确认流程。
- 底层物理删除、证据存留期限及正在阅读时的更新方式待细化。本规则替代第六轮概括性的“评论与子评论一并删除”和第七轮原建议的递归删除分支。

### DELETE-POST-01：删除帖子同时关闭讨论

- 2026-10-09用户明确本人删除成功后直接返回上一级页面，取消独立“帖子已删除／返回列表”页。确认且服务端删除成功后回到进入详情前的来源页，同步移除对应帖子并恢复原页签／筛选及可用列表锚点，不额外停留或要求再点返回。取消确认保留原帖；删除失败或结果未知不伪装成成功返回，继续保留原操作以便核对。当前两行宋体问题／左取消右亮红确认图见[本人删除确认记录](../ui-reviews/post-detail-states-v1.md)，仅静态图稿，真实删除及回退待验。
- 删除整篇帖子后，对外停止展示帖子内容及评论区，也不能继续发表评论或回复；不是只隐藏正文而保留一个可继续参与的评论区。作者的编辑入口随之移除，尚未保存的修改内容一并清除；已删除帖子不存在继续编辑的页面。
- 收藏、通知和分享入口统一显示“帖子已删除”，不从这些入口继续展示原帖内容；账号登录访问限制仍适用。
- 收藏中该占位可由本人移除，具体列表规则见[个人模块 PERSONAL-FAVORITE-01](personal.md)。
- 已经建立的私信继续保留并可聊天，不因来源帖子删除而关闭。
- 本规则决定产品可见性和交互；底层物理删除、保存期限、作者本人及评论者的私人归档视图另行确定。

### BLOCK-DM-01：按账号阻止私信，不公开身份关联

- 拉黑按对方所属账号生效，拉黑期间双方都暂停向对方发送私信；本人的其他身份同样受保护，双方不能通过切换身份绕过。
- 前台只展示本人选择拉黑的那副身份，不列出对方账号下的其他身份，不通过拉黑列表揭示面具关联。
- 已有聊天记录保留，允许本人解除拉黑。
- 设置中提供“黑名单”入口，显示当时选中拉黑的身份头像与昵称，并提供解除操作；不展示对方的其他身份。
- 发起拉黑的一方也须明确解除后才能继续发送，不因点击发送自动解除；在原拉黑会话提供解除入口，其他身份会话不提示其与黑名单身份的关系，不以解除提示暴露其他面具。
- 此规则仅限制私信，不自动扩展为公开帖子、评论或点赞的屏蔽。
- 会话列表长按菜单提供拉黑入口及“确认拉黑／举报／取消”底部面板，见[消息中心](messages.md)；设置黑名单提供解除入口。
- 被拉黑后的发送反馈只显示“暂时无法向对方发送消息”，不明确显示“你被拉黑了”，不披露其他身份。该文案不代表可以保证用户完全无法推断限制。拉黑完成前已被平台接受、尚未补投到接收方本地的消息仍按原投递任务补投；拉黑完成后的新发送直接拒绝。

### REPORT-01：内容举报入口与提交

- 帖子通过右上角菜单举报，评论和私信消息通过长按举报；会话拉黑的底部面板也提供独立“举报”入口。私信举报流程按 REPORT-DM-FLOW-01 执行，点击举报不自动确认拉黑。
- 举报类别提供“广告引流”“辱骂骚扰”“泄露隐私”“诈骗”“色情或违法内容”“其他”，共六类；允许补充文字说明。
- 提交成功后回到举报前的原页面，简短提示“已提交”；提交失败时留在详情页，保留本次类别、描述、聊天证据和补充图片，允许直接重试。具体返回路径和失败提示样式待设计。
- 举报对象是实际选中的帖子、评论或消息；私信证据授权范围按 REPORT-DM-FLOW-01 执行。举报人身份保护按 REPORT-PRIVACY-01 执行；审核处理与提交失败提示的具体表现待设计，不因提交举报就自动删除内容。提交后的案件在“系统通知”中保留本人可见的进度记录，可查看待处理、处理中、已结束和最终结果；不另设“我的举报”一级页签。
- [举报进度待处理 · 陶橘暖砂 v2 · 待评审](../../../UI产品图/私信举报-进度待处理-陶橘暖砂-v2.png)从系统通知的具体记录进入，只读展示待处理、举报与材料摘要；不改变提交成功返回原页的规则，不将已提交等同于举报成立。旧配色 E v1 被用户否决为颜色不足；v2 仅变更色彩与状态容器展示。
- [森林绿 v3 · 待评审](../../../UI产品图/私信举报-进度待处理-森林绿-v3.png)为同页下一套配色，布局与业务同 v2；不代表已选全局主题。

### REPORT-SUBMIT-UNKNOWN-01：提交结果未知先核对原任务

- 点击提交后结果未知时显示“正在确认提交结果”，自动查询原提交状态；仅确认未提交后才允许重试，重试沿用同一举报任务标识，避免重复创建。
- 核对为提交成功时按 REPORT-01 返回并提示；核对为未提交时保留本次材料供重试。仍未知不能仅凭超时断言未提交，也不能把退出页面当作撤销已收到的举报；异常关闭后的恢复入口及核对期间退出的具体界面待细化。

### REPORT-DM-FLOW-01：私信举报先选类别，再提交详情

- 第一步显示举报类别列表，用户选择类别后点击“下一步”，进入详情页。
- [选择原因 · 配色 A v1 · 待评审](../../../UI产品图/私信举报-选择原因-配色A-v1.png)：六项原因单选，演示用户选中“辱骂骚扰”；该状态不是默认选择。橙黑配色仅为试验，不代表全局配色定稿，流程规则不变。
- 第二步展示已选类别及说明，再填写举报详情、添加聊天证据与补充图片，最后点击“提交”。证据选择位于详情阶段，不前置到类别选择之前。
- [举报详情 · 配色 B v1 · 待评审](../../../UI产品图/私信举报-详情-配色B-v1.png)展示已选择聊天区间并主动授权的状态；不是默认勾选授权。保留重选与预览入口，文字及图片选填，苔绿配色仍为试验。
- 详情页包含聊天证据、举报描述、补充图片：聊天证据必选；描述选填，最多二百字；补充图片选填，最多六张。此上限仅用于举报材料，不改变帖子、评论或私信图片上限。
- 用户选择聊天证据后，须授权平台查看同一对身份会话中所选首条至末条区间内的全部可用记录，包含首尾消息、双方发言及中间未单独勾选的消息。完整记录按完整区间提交；本地有缺口时按 REPORT-DM-GAP-01 允许提交并明确标注，不能主动跳过仍存在的中间消息。
- [选择聊天证据 · 配色 C v2](../../../UI产品图/私信举报-选择聊天证据-配色C-v2.png)已按用户反馈改为左侧对方、右侧自己，保留起止标记、连续范围、重选和预览入口；用户要求改后直接继续。旧 [v1](../../../UI产品图/私信举报-选择聊天证据-配色C-v1.png)全左布局被替代。配色未定稿，不将选范围等同于提交授权。
- 用户修正消息排版：证据选择和证据预览中的消息按聊天方向展示，**左边对方、右边自己**，按时间上下排列；不再把双方消息都放在同一左对齐列表。此项仅改变展示，不改变首尾区间、双方记录纳入、证据快照或授权范围。用户要求修改后直接继续下一张，不追加询问。
- 详情页通过默认未勾选的授权框，明确说明将提交所选首条至末条区间内的可用聊天记录及已知缺口，并允许预览本次授权的记录；预览时固定本次证据按 REPORT-DM-SNAPSHOT-01，用户确认授权后再提交。此授权不扩展到起止范围之外或其他身份的会话。
- 授权框与预览的具体排版、证据异常处理待设计。提交失败按 REPORT-01 保留本次填写内容，不要求重新填写。

### REPORT-DM-GAP-01：本地聊天有缺口仍可举报，明确标注

- 本地曾删除消息导致所选区间有缺口时，仍允许提交举报；预览及审核材料必须明确标注已知缺口，不能声称记录完整。此项放宽原“必须完整连续记录”的前提，不取消区间授权和预览要求。
- 审核员结合缺失情况判断证据，不默认平台能补回缺失原文；不将不知道是否缺失的记录保证为绝对完整。缺口识别与标注方式待实现设计。
- 不因允许缺口就扩大到未授权区间或其他身份会话；用户改选区间仍须更新预览并重新授权。


### REPORT-TARGET-01：举报目标删除后的处理

- 被举报帖子或评论已删除时，未处理完的举报流程终结，不继续保持待处理或审核中；已经处理完的结果与记录保持不变。
- 终结不等同于认定举报成立，也不自动撤销已有处罚。
- 私信一方清空自己的聊天记录不终结已提交举报；对方记录和已经授权提交的证据仍按既定范围处理。此例外已由用户确认，不因一方删除本地会话而使审核证据失效。
- 因帖子或评论删除而终结时，给举报人发送“内容已删除，本次举报已结束”，不标为举报成功或失败。审计及删除与处理同时发生的顺序待细化。

### REPORT-EVIDENCE-01：提交后保留当时的举报证据

- 举报成功提交后，保留当时提交或授权的证据；后续帖子编辑或私信撤回不使这份证据失效，仍可依据举报时的内容审核。
- 私信证据仍限于用户明确授权的连续记录范围，不能借此扩展到其他区间、其他会话或所有历史版本。
- 帖子或评论直接删除仍按 REPORT-TARGET-01 终结未完成举报；证据保留不改变这个已确认例外，也不向普通读者开放历史版本。
- 证据保存期限、提交和修改同时发生时的顺序及异常反馈待细化。

### REPORT-DM-SNAPSHOT-01：预览时固定私信举报证据

- [证据预览 · 配色 D v1 · 待评审](../../../UI产品图/私信举报-证据预览-配色D-v1.png)：按左对方／右本人预览所选区间，“更改范围”回到选择，“使用这份证据”返回举报详情，确认授权后才提交。该图不代表自动授权或锁定全局配色。
- 用户预览所选连续聊天区间时，固定本次预览的证据；最终授权提交的是这份记录，不能在用户填写说明期间悄悄替换成另一版本。
- 预览后、提交前，对方撤回了范围内消息，仍可提交刚才预览的证据，后续撤回另行标注。用户最终授权提交后才进入审核，不在授权前供审核员查看。
- 固定范围仍包含所选首尾及中间全部可用记录，存在已知缺口时一并固定缺口标注，按 REPORT-DM-GAP-01，不扩展到其他会话或未选区间；改选证据范围时更新对应预览并清除原授权勾选，用户须确认新范围后重新授权，已经填写的说明和补充图片保留。未提交的临时副本需要清理，保存位置、清理时限与异常恢复待细化。
- 本规则针对私信举报；公开帖子或评论删除终结未完成举报的规则继续适用，不因本规则恢复已删除公开内容的举报。

### REPORT-LEAVE-01：有材料时确认放弃，清理未提交材料

- 用户已填写说明、选择证据或添加图片后，主动退出整个举报流程时先确认是否放弃；确认放弃后清理本次未提交的材料及临时证据，不建立长期举报草稿。
- 取消放弃则留在流程内保留材料；临时切后台不视为主动放弃。提交明确失败仍按 REPORT-01 保留输入和证据供重试，不套用放弃清理。
- 已成功提交的举报不受本规则影响；未提交材料不供审核员查看。结果未知按 REPORT-SUBMIT-UNKNOWN-01 先核对；临时副本实际清理时限、异常关闭及核对期间退出的界面仍待细化。

### REPORT-PRIVACY-01：不向被举报方展示举报人身份

- 平台不向被举报方展示举报人身份。
- 给举报人的处理结果包含结论及简短原因，不披露对方平台编号、其他身份或处罚历史。
- 如需向被举报方通知处理结果，只说明违规内容与处理措施，不透露举报人信息。

### ADMIN-PRIVACY-01：匿名审核与处罚

- 普通审核员可审查被举报内容及授权证据，不可查看完整邮箱或账号的其他面具；管理端新增可识别字段按 ADMIN-DISPLAY-01 执行。
- 所有管理端均不得获知完整验证邮箱，不提供高级管理员解锁的例外；仅展示平台编号，不显示打码邮箱及验证匹配标记。认证隔离和最高权限边界见[账号模块](accounts.md)。
- 管理处罚需要稳定定位目标，但不以显示实名、邮箱或其他身份列表为前提；技术实现尚未选定，不承诺仅隐藏页面字段即可抵御基础设施最高权限。

### ADMIN-ROLE-01：审核员与管理员

- 审核员处理举报、下架内容、重置违规身份资料和限时禁言；管理员在此基础上额外负责封号、解除封禁和权限管理。
- 两类角色都不能查看完整邮箱、打码邮箱及验证匹配标记；案件证据仍受授权范围限制。
- 复核与恢复内容的具体授权、权限变更及后台操作界面待细化。

### ADMIN-DISPLAY-01：仅以平台编号识别匿名账号

- 管理后台用六位平台编号识别账号，格式由[账号模块 AUTH-ISOLATION-01](accounts.md)维护；不显示或下发邮箱原文、打码邮箱、资格槽位及内部账号映射。按注册顺序递增的分配方式会泄露大致注册次序，实施前须复核。
- 本方案已获用户确认，取代先前“管理编号加脱敏邮箱”的方案。工单编号仍用于区分举报事项，与平台账号编号分工不同。
- 允许管理员识别同一匿名账号，不自动开放该账号所有面具或历史内容的查看权限，仍按 ADMIN-PRIVACY-01 审查被举报内容和授权证据。
- 每次新注册的校邮资格配额由独立验证方处理；日常以私有用户名密码登录 C，不能由管理员按邮箱查询、恢复或重设旧号，见[账号模块 AUTH-LOOKUP-01](accounts.md)。管理员通过平台编号处理违规。
- 六位编号、账号列表查询、违规记录与 ADMIN-AUDIT-01 的操作记录已确认；编号分配方式、具体页面与授权检查待细化。

### ADMIN-ACCOUNT-01：账号列表、查询与违规记录

- 账号列表显示平台编号、注册时间、账号状态、已确认违规次数和操作入口；收到举报不直接计为违规。
- 支持按平台编号查找账号、按工单编号查找举报事项，不提供邮箱反查。
- 管理员可查看该编号的既往处罚及对应案件，以判断重复违规；案件证据仍按权限查看，不自动开放所有私信或其他面具列表。
- 申诉通过后修正对应的违规次数，按 MOD-REVERSE-01 执行；同一内容、同一事实的重复举报归并按 REPORT-DUPLICATE-01，筛选排序及具体界面待设计。

### REPORT-DUPLICATE-01：同一违规事实的举报合并处理

- 同一内容、同一违规事实被多人举报时，合并处理，只形成一次违规认定及相应处罚；不因举报人数或多名审核员同时处理而重复计违规、重复加罚。
- 每位举报人分别收到对应处理结果，继续保护举报人身份；收到举报本身仍不直接计为违规。
- 不同违规事实、内容修改后新增违规及已结案后新增证据的划分待细化；案件合并和同时操作须防止重复处罚，具体实现待设计。

### MOD-CONCURRENT-01：同一举报先成功处理，后提交提示已处理

- 多名审核员同时处理同一举报时，提交动作进行服务端并发校验；先成功的处理形成案件结果，后提交者看到已处理状态，不能重复叠加处罚。
- 有明确新事实或需要由更高权限人员升级处理时，另按相应权限和案件流程处理，具体路径待细化。更高权限不取消 REPORT-DUPLICATE-01 的同一事实不重复处罚规则，也不能直接覆盖已完成结果而不留记录；继续遵守 ADMIN-ROLE-01 与 ADMIN-AUDIT-01。

### ADMIN-AUDIT-01：记录管理员操作

- 记录执行管理员、操作时间、目标平台编号、具体动作及原因，便于追查误操作。
- 操作记录遵守邮箱及身份隐私边界，不借审计字段保存完整邮箱或展示其他面具列表。
- 查询权限、记录保存期限及防篡改实现待细化。

### MOD-ACTION-01：基础处理措施

- 后台提供下架内容、限时禁言及封禁账号三种处理，按 ADMIN-ROLE-01 授权并填写原因。管理员下架与用户主动删除区分，误判下架可按 MOD-REVERSE-01 恢复。
- 禁言提供一天、三天、七天、三十天，由管理员选择并填写原因，不根据举报数量自动处罚。
- 禁言暂停发帖、评论、编辑已发布内容、发送私信和点赞；仍允许浏览、收藏、举报、申诉及删除自己的帖子和评论。账号级处罚对所有身份生效；禁言期间允许申请注销，遵循[账号模块 ACCOUNT-CLOSE-ELIGIBLE-01](accounts.md)。七天注销缓冲期间禁言继续生效；正式注销完成时该账号禁言随账号终止，不延续到之后重新注册的新账号。
- 封禁提供一天、三天、七天、三十天及永久五档，管理员必须填写原因；有限期封禁到期解除对应限制，其他有效处罚继续执行。永久封禁不自动到期，只能经有权限人员按既定流程解除。
- 封禁后保留处理原因、期限与申诉入口，其余社区功能不可用；封禁仍生效时不能申请注销，遵循[账号模块 ACCOUNT-CLOSE-ELIGIBLE-01](accounts.md)。不采用曾提出的九十天档位。
- 操作审计按 ADMIN-AUDIT-01 记录；不同角色授权及提交异常待细化。
- 注销账号不会自动触发删除内容，注销的保留与头像提示按[账号模块 ACCOUNT-CLOSE-01](accounts.md)执行。

### MOD-PROFILE-01：违规昵称或头像重置

- 昵称或头像本身违规时，沿用现有举报入口反馈；审核员可将违规项重置为中性占位，并通知本人。只处理违规的对应资料，不因一个身份违规而展示或重置其其他身份。
- 用户可立即修改为合规资料；本次强制整改不受昵称三十天修改间隔限制，正常自主改名仍按[身份 MASK-EDIT-01](identity.md)执行。
- 资料重置不删除身份，不改变已有内容和会话归属；需要禁言或封禁时，继续按既有角色权限与 MOD-ACTION-01 处理，不因资料重置自动新增账号处罚。
- 处理原因与操作按 ADMIN-AUDIT-01 记录。此项由[第二十一轮 Q2](../../discussions/2026-09-19-grilling-round21.md)确认。

### MOD-TAKEDOWN-01：下架帖子不提供整改重审

- 首版不允许对管理员已下架的帖子修改后重新审核，也不能通过普通编辑保存恢复公开。
- 认为原处理误判时仍可按 APPEAL-01 申诉；复核通过后的恢复条件继续按 MOD-REVERSE-01，不因取消整改重审而取消申诉恢复。
- 本项不新增自动解除处罚的路径，不把管理员下架等同于作者主动删除。此项由[第二十一轮 Q3](../../discussions/2026-09-19-grilling-round21.md)确认。

### MOD-TIME-01：各项处罚独立计时，不顺延累加

- 每项处罚从作出时独立计时；同类处罚有重叠时，不将新处罚接在旧处罚剩余时间之后。对应限制持续到所有相关有效处罚结束，或按既定权限被解除。
- 例如禁言尚余三天，又因另一案件作出七天禁言，则从新处罚作出时起最长还需七天，不自动累加成十天。永久封禁仍不自然到期。
- 管理员提交处罚前可看到考虑现有处罚后的预计恢复时间；需要更重处罚时，应明确选择相应档位并填写原因，不依赖隐含的时长累加。
- 每项处罚的申诉与撤销继续独立处理，解除其中一项不影响其他有效处罚。并发提交、执行失败及恢复界面另行细化。

### APPEAL-01：处理通知与申诉

- 举报反馈与违规处理结果通过[消息模块的系统通知](messages.md)送达。
- 违规处理通知提供“申诉”入口，用户补充说明后交由另一名有相应权限的管理人员复核；原处理人可提供说明，不能独自决定针对自己原处罚的申诉结果。
- [违规处理通知详情 v1](../../../UI产品图/系统通知-违规处理通知-v1.png)已于 2026-09-20 获用户确认：涉及内容及状态、处理原因、措施、本次起止期限、账号影响范围及底部申诉入口。示例中的三天禁言不代表固定处罚；申诉入口不直接提交或消耗次数。
- 同一处罚同时只能有一份待处理申诉，用户可补充材料；处理结果必须说明理由。
- [待复核详情 v1](../../../UI产品图/申诉-待复核详情-v1.png)已获用户确认：显示状态、处罚摘要、本次次数、已提交材料与时间，底部提供“补充材料”入口及本次额度提示。不承诺完成时限，不将提交成功当作申诉通过，不改变处罚执行。
- 处罚到期而申诉尚未结束时，先解除该处罚对应的限制，申诉继续处理；通过后仍修正违规记录，不因处罚已到期就停止复核。其他有效处罚不受影响。
- 被封禁用户仍可访问处理通知和申诉页，其余社区功能按 MOD-ACTION-01 限制。
- 首次申诉最多五百字、六张图片；处理中每次追加最多五百字、三张图片，不计入首次额度；案件结案后不再追加材料；结案后出现新证据不能追加到已结案的那次申诉，可发起新一轮申诉；涉及独立违规事实时另行举报，不以重复举报绕过申诉次数。各次补充独立保存，不覆盖先前提交；页面按本次额度显示剩余容量。
- 不采用首次及所有追加合计五百字、六张图的限制；每次追加按提交时间接在原材料下方，独立成组，不覆盖此前内容。
- [补充材料 v1 · 待评审](../../../UI产品图/申诉-补充材料-v1.png)展示本次独立额度、当前申诉及待复核状态、输入区和提交补充材料入口；不改变计数、退出保存或空表单校验规则。
- 用户进一步明确：先提交一份申诉，再追加一批图片，合计仍为一次申诉。每次独立发起申诉计一次，追加只是补充，不占三次申诉额度；追加次数没有已确认的额外限制。
- 结案后有新材料可再次申诉，沿用原工单并保留既往处理记录；针对同一处罚累计最多申诉三次，包含首次，切换身份不增加次数。同时最多一份待处理申诉继续适用。
- [结果未通过 v1 · 已确认](../../../UI产品图/申诉-结果未通过-v1.png)为首次申诉未通过且仍有额度的示例：显示理由、原处罚及期限维持、新材料要求与再次申诉入口；用户答复“可以，下一张”，此图定稿。入口不直接提交，已结案申诉不能追加，计数和处罚计时不变。
- 暂时没有另一名有权限人员复核时，申诉保持“待复核”，等有权限的其他人员处理；不让原处理人自行驳回，已提交材料继续保留，也不额外消耗一次申诉。
- 复核回避与人员暂缺的等待规则已确认；新材料判断、人员调配和具体页面待设计，不预先承诺完成时限。
- 继续遵守 REPORT-PRIVACY-01，不向被举报方透露举报人身份。


### APPEAL-DISPLAY-01：紧凑显示申诉次数

- 用户最终选择“申诉 1/3”形式，分别表示当前第一次、第二次或第三次独立申诉；此选择替代此前用“第一次申诉”等完整文字的方案。
- 2026-09-20 用户修正次数的展示位置：页面主标题只写“申诉”，不将“1/3”写在大标题中；次数放入次要说明区域。修订稿建议置于处罚摘要下方，以“本次申诉 1/3”配合额度说明展示，具体图稿待评审。只调整位置和层级，不改变三次上限或计数口径。
- [首次申诉提交 v2 · 待评审](../../../UI产品图/申诉-首次提交-v2.png)已按该反馈生成；[v1 旧稿](../../../UI产品图/申诉-首次提交-v1.png)的标题位置被否决，不能恢复。
- 同时说明“最多可申诉 3 次，补充材料不占次数”；不能把追加一批图片算作下一次申诉。
- 数字是次数说明，不表示审核完成进度。具体排版随申诉页面设计，当前消息首页图不包含申诉页面。

### MOD-REVERSE-01：申诉通过后撤销对应处罚

- [结果通过 v1 · 已确认](../../../UI产品图/申诉-结果通过-v1.png)展示复核理由、对应处罚撤销、符合恢复条件的评论恢复及违规记录修正。用户答复“可以下一张”，此图定稿。仅为本规则的示例视觉稿，不代表全部申诉都可恢复内容。
- 申诉通过后解除对应处罚，修正已确认违规次数，并向用户发送处理结果。
- 其他仍有效的处罚继续执行，不能因一项申诉通过就解除所有限制。
- 申诉通过后恢复仅因本次误判下架的内容；用户已经主动删除，或仍有其他有效下架原因，则不恢复。处罚撤销和内容恢复保留操作审计，计数及恢复并发待实现设计。
