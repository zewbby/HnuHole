- 文件 SHA-256：`da913014063f3972dbc15a6c79a87757e7f113ff9cd5911bbb4b42918e5262b1`。任何字节变化都须更新[静态复验记录](../../packages/auth-protocol-vectors/static-verification-report.json)并重跑受影响案例。
- `keys[].testSeedHex` 是公开的 32 字节种子，不是一些库使用的 64 字节 secret-key 格式。前三组来自 [RFC 8032 §7.1](https://www.rfc-editor.org/rfc/rfc8032.html#section-7.1)，第四组是公开递增字节。恢复秘密、令牌、挑战、意图与受控时钟也全部是合成输入，严禁进入生产配置。

- `timeCases` 仅检查规定的整数桶边界；`stateCases` 的 12 项尚未在实际服务、SQL 或客户端上执行，均标为 `..._PENDING`。本轮复验不证明锁、持久化、outbox 或灾备成立。

## 2. 字节和传输格式

hex 为无前缀、小写、偶数长度。wire 是 [RFC 4648](https://www.rfc-editor.org/rfc/rfc4648.html#section-3.5) 规范无填充 base64url；拒绝 `=`、空白、标准 `+/`、非零尾位和错误字节数。解码后须重编码一致，不能只靠宽松库“解码成功”。

| 用途 | 正文长度 | 传输字节 | base64url 长度 |
| --- | --- | --- | --- |
| `REGISTER/V2` | 92 | 正文＋64 字节 V 签名＝156 | 208 |
| `RETIRE-AUTH/V1` | 59 | 正文＋64 字节 V 签名＝123 | 164 |
| `RETIRED/V1` | 55 | 正文＋64 字节 C 签名＝119 | 159 |
| `RELEASED/V1` | 56 | 正文＋64 字节 C 签名＝120 | 160 |
| `BOOTSTRAP-POP/V1` | 153 | 仅传 64 字节 bootstrap 签名 | 86 |

`REGISTER/V2` 以零起始偏移解析：

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 20 | ASCII `HNUHOLE/REGISTER/V2`＋`0x00` |
| 20 | 4 | `v_key_epoch`，u32 大端；合成值 `0x01020304` |
| 24 | 4 | `admission_window`，u32 大端；合成值 `1000000` |
| 28 | 32 | `slot_id` |
| 60 | 32 | `pk_boot` |
| 92 | 64 | 对前 92 字节的 V 签名 |

`wireBytesHex/wireBase64url` 是实际传输内容，`wireKind` 区分完整票据与仅签名。PoP 正文由 C 从不可修改的意图重建；**不存在 217 字节的 PoP 票据**。PoP 的末尾散列覆盖完整 156 字节注册票据，含 V 签名；不散列 JSON，也不只散列票据正文。替换意图、挑战或票据而保留旧 PoP 必须失败。

槽位输入含域后的零字节及算法字节 `0x01`；整数大端规则只用于协议 u32。Ed25519 的压缩点与 S 仍采用其标准编码，不能把 S 改为大端。

## 3. 项目的 Ed25519 接受配置

为避免“严格”由不同库自行解释，所有 bootstrap／V／C 签名使用同一配置：

1. 签名恰 64 字节，分为 32 字节 `R` 和 32 字节 `S`；公钥 `A` 恰 32 字节。
2. `A` 和 `R` 都能规范解码为曲线点，拒绝 `y≥p`、`x=0` 却置符号位等别名；都非单位元，且 `[L]P=I`。这排除小阶与混合阶点。受信 V/C 公钥在导入配置时也校验，不能因“内部配置”跳过。
3. `0≤S<L`，S 按 32 字节小端读；不能取模后接受 `S+L`。
4. 对固定原始正文执行 **Pure Ed25519** 验签，`k=SHA-512(R||A||M) mod L`，要求 `[S]B=R+[k]A`；不得改用 ctx/ph 或先对整段正文求 SHA-256 再签。

这是 [RFC 8032 §5.1.6–5.1.7](https://www.rfc-editor.org/rfc/rfc8032.html#section-5.1.6) 基础规则之上的项目接受配置，主动拒绝理论上可有效的单位元 R，不宣称接受所有 RFC 有效签名。A/R 都处于阶 L 子群后，8 在该子群可逆，因而 cofactored 与 uncofactored 方程等价；这是对所选配置的数学推论，仍待独立核对。

配置只定义验收谓词；生产必须选成熟原语与点验证接口、锁定版本并跑向量，不自行实现曲线解码、群运算或签名算法。仅检查“非小阶”不能排除混合阶点；仅调用 `Verify` 也不能证明已执行上述准入。

## 4. 库差异与本轮实测

本轮使用 PyNaCl **1.6.2** 与 Node **v24.11.1**／OpenSSL **3.5.4**，分别独立从种子派生钥、生成签名、验证输入；不是 Go/Flutter 运行证据，也未选为生产认证组合。临时核验器执行了 496 个断言，数量包含数据格式检查，不能换算成覆盖率。库调用、版本和输入散列见[复验记录](../../packages/auth-protocol-vectors/static-verification-report.json)。

| 反例 | Node/OpenSSL 裸 Verify | PyNaCl 裸 Verify | 本次 PyNaCl 公钥点检查 | 项目接受 |
| --- | --- | --- | --- | --- |
| 单位元 A | true | false | false | 否 |
| negative-zero 单位元 A | true | false | false | 否 |
| `y=p+1` 非规范单位元 A | true | false | false | 否 |
| 混合阶 `B+T₂` A | true | true | false | 否 |
| RFC 控制签名改为 `S+L` | false | false | — | 否 |
| RFC 控制签名的 R 改为 `y=p+1` | false | false | — | 否 |

每一例完整的 `A/M/signature` 和实际结果都在 JSON。反例是合成消息上的库接受差异，没有向真实 C 发起攻击。单位元 A 可使 `R=B,S=1` 对任意消息通过某些宽松验签；混合点不是小阶点，不能用“已拒小阶”作保证。

[libsodium 官方点校验文档](https://doc.libsodium.org/advanced/point-arithmetic)披露旧版 `≤1.0.20` 会误收部分混合阶点，并给出 `((L−1)P)+P==I` 的补充核对。本轮用成熟 API 及该核对；本次 PyNaCl wheel 的点检查确实拒绝混合点，不从绑定版本推断底层库细分版本。未来生产组合须复验固定编译产物，升级或换平台后也重跑；不得直接把未经核对的 `is_valid_point` 名称等同于完整配置。

## 5. 独立复验步骤与验收

1. 锁定本轮完整提交、向量文件散列及运行库版本。先校验 JSON 无重复键、ID 唯一、hex 和 wire 格式；语法检查 `python3 -m json.tool packages/auth-protocol-vectors/v1.json` 只证明 JSON 可解析。
2. 用成熟库从每个 32 字节公开 seed 派生公钥；先逐字复现三个 RFC 控制，再按协议独立拼接正文并逐字复现八组签名。不要把生成器代码当作唯一预期值来源。
3. 对公钥与 R 分别运行点准入，对 S 检查范围，再验原消息。11 个错误签名、22 个点案例和 6 个库行为案例逐一记录；宽松库的 true 是待封堵差异，不能作为项目接受结果。
4. 独立重算槽位、完整票据散列、七种能力／墓碑摘要与规范编码。有效 V 签名但槽位／公钥不匹配时拒绝；恶意 V 使用全新钥与对应新槽位仍可通过格式绑定，这属于已接受的假资格边界。
5. 固定时钟下核对桶边界：本桶起点至下一桶末秒接受，第二次换桶立即过期；未来 1／60 秒拒绝并提示原票重试，61 秒按时钟故障处理。等锁跨过期点须拒绝，回退须冻结。当前只有算术证据，取得 SQL 锁后重新取时仍需真实交错测试。
6. 将 12 个状态案例及评审包 A01–A19 转成后续真实服务／事务／客户端测试，保存故障位置与已提交状态；尚无实现时不标通过。用途、环境钥、撤销列表及唯一约束也不能由单纯验签证明。

本轮只完成静态材料内部复验。下一项应产生新证据：确定真实评审者和 V/C 运营关系，按[评审包](auth-privacy-security-review-package.md)核查；获得实施授权后再做隔离环境中的 SQL 约束与注册／退役 outbox 验证。
