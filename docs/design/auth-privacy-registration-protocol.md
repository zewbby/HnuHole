# Hnuhole 校邮资格、开户与槽位释放协议 v1

日期：2026-09-28。状态：**实施前协议规格；未实现，未经过独立安全审计。** 本文细化[认证与隐私架构决策](auth-privacy-architecture-decision.md)的注册及配额生命周期；密码与独立恢复规则见[恢复决策 v1](auth-privacy-recovery-decision.md)，逻辑数据与接口见[数据与 API 契约 v1](auth-privacy-data-api-contract.md)，内部攻击路径见[跨方威胁模型](auth-privacy-threat-model.md)。本文作为首版协议文档，注册资格的**消息格式已升为 `REGISTER/V2`**；无期限的 `REGISTER/V1` 从未生产使用，必须拒收。V/C OpenAPI 与[数据库迁移设计](auth-privacy-database-migration-design.md)已成稿；生产认证代码仍须等待契约／实际SQL审阅、部署安排和独立安全评审通过。

## 1. 目标与信任边界

每次新账号注册，用户向独立校邮验证方 V 提交一次学校邮箱验证码；V 为该**精确邮箱地址**维持至多一个当前资格槽位。社区方 C 只根据 V 的签名资格和客户端持钥证明开户，不收邮箱。日常登录或旧号恢复由 C 的用户名密码和事先设立的独立恢复凭据负责，不能回退到邮箱 OTP。注销后新注册须再次收码，使用全新槽位。

本协议要求 C 诚实执行唯一约束、原子事务与旧票拒绝记录，要求客户端在注册期间保管一次性私钥并验证 C 的真实连接。V 可以主动恶意；设计只阻止它用**用户的同一槽位**替换公钥并抢先兑付。V 仍可自造新密钥、新槽位和假资格、占用配额、阻止用户注册或泄露其持有的邮箱数据。这符合已接受的“可造新号、不能仅凭校邮接管旧号”边界；严格一邮箱一号的保证只在 V 按协议执行时成立。C 若主动恶意、客户端被篡改、V/C 串通或双方数据合并，也不在单侧隐私保证内。[Privacy Pass 架构 RFC 9576](https://www.rfc-editor.org/rfc/rfc9576.html)说明隐私性质依赖参与方部署和非串通前提；本文不是 Privacy Pass 协议实例。

## 2. 固定编码与密钥

- 客户端为**每一次新资格／新槽位申请**用安全随机数产生全新的一次性 Ed25519 密钥对 `(sk_boot, pk_boot)`，不得主动复用旧公钥。同一槽位因用户名冲突、C 挑战过期或网络重试而重新建立待开户意图时，继续使用原密钥与资格。V 在签发前、C 在验票前按第 2.1 节统一检查公钥准入，全部签名遵循同一接受配置；不支持的算法拒绝。仅检查“可解码成曲线点”或单独调用宽松 `Verify` 不足以证明持钥安全；弱点公钥可能让伪造的 PoP 通过。C 依槽位终态拒绝旧公钥复用。一次性私钥只在本地用于开户持钥证明，成功后安全删除，不能兼作日常登录或旧号恢复凭据。
- `slot_id = SHA-256(ASCII("HNUHOLE/SLOT/V1") || 0x00 || 0x01 || pk_boot[32])`，其中 `0x01` 固定表示 Ed25519。输出为 32 字节；客户端和 C 独立重算，V 只能签这个值，不能要求客户端采用 V 提供的槽位。使用 [FIPS 180-4 的 SHA-256](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)和 [RFC 8032 的 Ed25519](https://www.rfc-editor.org/rfc/rfc8032.html)；“换公钥却保持同一槽位不可行”是依赖散列第二原像／碰撞阻力的本协议推论，仍须审计组合设计。
- 所有待签名消息均为**固定字节序列**：下列 ASCII 作用域后紧跟 `0x00`，整数为无符号 32 位大端，`slot_id`、公钥、挑战、意图 ID 和散列值均为固定 32 字节。消息不得有可选字段、自由文本、邮箱、账号 ID、精确签发时间、设备标识或由 V 按人选择的扩展字段；注册资格只允许下条统一的粗粒度准入窗口。未知版本和多余字段一律拒绝。V 与 C 的签名私钥和受信公钥配置分别管理，不共用签名用途。
- V 注册资格的消息 `REG_MSG` 为 `"HNUHOLE/REGISTER/V2" || 0x00 || v_key_epoch:u32 || admission_window:u32 || slot_id[32] || pk_boot[32]`。`admission_window = floor(V 完成 OTP 验证时的 UTC Unix 秒 / 1800)`，是所有用户共用的三十分钟桶，不能由客户端传入或由 V 按用户挑选；`registration_ticket_bytes = REG_MSG || v_signature[64]`，没有其他字段。客户端核对返回的公钥和槽位等于本地生成值；C 验 V 签名、受信的全局密钥版本、格式及槽位散列等式。C 在创建待开户意图及最终开户事务的锁内裁决点，以实际数据库时间重新计算当前桶，都只接受**本方当前桶或紧邻上一桶**；不能沿用事务开始时刻，未来桶和更早桶一律拒绝。因此票据从 OTP 验证起最多约六十分钟、最少约三十分钟有效，不能无限期代表当前校邮控制。V/C 须由独立授时源监测 UTC 偏差，并使 C 的已接受时间高水位不可随备份回退；C 检出时钟倒退或无法确认真实时间时停止验票，不能让已过期资格重新有效。V 比 C 快数秒、刚跨桶时，C 仍拒绝未来桶，但可提示原票在本桶开始后短时重试，不要求再次收码；异常大偏差按时钟故障处理，不能因单张未来票放宽验收窗口。旧 `REGISTER/V1` 未投入生产，C 从本修订起拒收该无期限消息。密钥版本是全局轮换批次，不得按邮箱、用户或单张资格挑选。
- 取消授权消息为 `"HNUHOLE/RETIRE-AUTH/V1" || 0x00 || v_key_epoch:u32 || old_slot[32]`，由 V 签名；C 只把它用于**尚未开户**槽位的退役。C 的退役收据为 `"HNUHOLE/RETIRED/V1" || 0x00 || c_key_epoch:u32 || old_slot[32]`；正式注销释放收据为 `"HNUHOLE/RELEASED/V1" || 0x00 || c_key_epoch:u32 || old_slot[32]`，分别由 C 签名。用途与密钥版本必须验明，退役不能冒充正式注销，释放也不是新注册资格。
- 注册持钥证明的消息为 `"HNUHOLE/BOOTSTRAP-POP/V1" || 0x00 || slot_id[32] || intent_id[32] || challenge[32] || SHA-256(registration_ticket_bytes)[32]`，由 `sk_boot` 签名。这里 `registration_ticket_bytes` 是上条唯一的固定编码资格全文；它的散列不是密码散列。持钥证明中**不放裸密码、可快速计算的密码散列或恢复码**，避免签名本身成为离线试密码材料。

这套固定编码是本项目的协议定义，不把 [RFC 9449 的 DPoP](https://www.rfc-editor.org/rfc/rfc9449.html) 误称为现成注册协议；该 RFC 对公钥绑定、一次性 nonce 和重放防护有可参考的经验，也明确持钥证明本身并不是客户端身份认证。

### 2.1 Ed25519 的项目接受配置

这里的“严格验签”统一指以下全部条件，对 bootstrap PoP、V 资格／退役授权、C 退役／释放收据一致执行：

- 公钥 `A` 为恰 32 字节的规范压缩曲线点，能解码、非单位元且 `[L]A=I`；拒绝 `y≥p`、`x=0` 却置符号位、单位元、小阶与混合阶点。V/C 受信公钥导入配置时也验证，不能因来源是内部配置而跳过。
- 签名恰 64 字节；前 32 字节的 `R` 遵循与 A **相同**的点准入，含非单位元及 `[L]R=I`。后 32 字节的 `S` 是小端整数，须 `0≤S<L`，不能先取模。
- 使用 **Pure Ed25519** 对上述原始正文验签：`k=SHA-512(R||A||M) mod L`，要求 `[S]B=R+[k]A`；不用 ctx/ph，也不先对整段正文求 SHA-256 再签。`I` 为单位元，`B` 为标准基点，`L=2^252+27742317777372353535851937790883648493`。

该配置在 [RFC 8032 §5.1.6–5.1.7](https://www.rfc-editor.org/rfc/rfc8032.html#section-5.1.6) 基础上收紧，明确拒绝理论上有效的单位元 R；不宣称接受所有 RFC 有效签名。A/R 均在阶 L 子群时，cofactored 与 uncofactored 验证方程等价。实现必须选成熟库及点验证接口，锁定构建并跑[固定向量与库差异案例](auth-privacy-protocol-vectors.md)，不能自行实现曲线算法或把某个 API 名称当成已满足配置。仅检查非小阶不足以排除混合阶；[libsodium 官方说明](https://doc.libsodium.org/advanced/point-arithmetic)还披露部分旧点检查版本的子群缺陷，所选实际产物须通过负向复验。

## 3. 正常注册

1. 客户端先生成 `sk_boot/pk_boot` 和 `slot_id`，只把精确邮箱、V 的 OTP 操作所需材料、`slot_id` 和 `pk_boot` 发给 V；用户名、密码、恢复材料不发给 V。V 独立重算槽位散列等式，并对邮箱格式、OTP 和该地址的当前配额做原子检查。空闲时先同事务持久登记 OTP 消费、`email → RESERVED(slot_id, pk_boot)`、固定 REG_MSG／原准入桶和签名待办；提交后由 HSM 签名，签名持久后才返回资格。待签为 `202 CONFIRMATION_PENDING`，不能在 SQL 持锁期调用外部签名服务；签名延迟不前移准入桶，到期须新 OTP 同槽位换签。响应丢失不能额外签出另一槽位。**同一已验证确认请求**在 V 保存的十分钟幂等窗口内可用原幂等键取回原资格，不重新收码；窗口过后、票据过期或重新进入注册流程须再次验证 OTP，仍持本次私钥者取得**相同槽位／公钥、当前窗口的新签名资格**。旧票即使还在原设备也不延长有效期。例行换钥时可在新 OTP 后为同一槽位／公钥换签，不新开槽位。V 拒绝同地址未释放情况下的新槽位。
2. 客户端核对 V 返回的公钥和槽位，再由用户设置私有用户名和独立密码。C 收到资格及开户材料后，先验签、验证散列等式和格式；密码只经认证 TLS 进入 C，C 以独立盐和 Argon2id 形成验证值。C 建立**最长十分钟、不可修改**的待开户意图，保存该资格、用户名、密码验证值及恢复凭据配置的绑定关系，随机产生 `intent_id` 和 `challenge` 各 32 字节，并生成一次性展示的 128 位恢复码、仅保存其摘要。用户隐藏原码后完整重输，C 在最终开户前校验确认值；意图响应丢失时重新建意图和新码，不能重发原码。过期后 C 删除该待开户意图内的敏感材料；意图或挑战过期只影响本次证明，**不能自动释放 V 的邮箱配额或使槽位可再次开户**。C 对待开户意图的创建数量与失败次数限速；单纯创建意图不能占用槽位。
3. 客户端只接受从应用可信配置中的 C 端点、经认证连接取得且与自己这次开户意图对应的挑战，用 `sk_boot` 对上述持钥证明消息签名；不能让 V 的响应指定 C 端点。不能签 V、邮件、网页跳转或其他来源给出的任意挑战。C 只能从已保存的不可修改意图取得最终开户材料，不在证明提交时接受替换用户名、密码或恢复材料。
4. C 在单一事务中验资格窗口仍有效、挑战未过期、证明正确、意图未消费、私有用户名可用、恢复码确认与意图内摘要相符，以及该槽位从未被开户或退役；然后原子创建账号、消费该槽位和挑战，并建立单设备会话。槽位唯一约束是最后裁决；并发请求只能有一个成功。已验证的证明若因用户名冲突或其他前置条件被拒，C 也须持久标记该意图／挑战已处理，但**不消耗槽位**；用户可用同一资格和私钥创建新意图重试，须重新取得挑战并受限速约束。若资格在十分钟意图内过期，C 拒绝最终提交、废弃该意图与旧恢复码，保留未消费槽位；客户端重新收码取得同槽位／公钥的新票、挑战和恢复码，旧 PoP 因绑定旧票不能复用。事务未提交时按结果未知重试核对。**不能仅凭签名资格、已用挑战或 bootstrap 私钥登录已有账号。**
5. C 注册事务已提交但响应丢失时，不重新发放原会话令牌，也不依靠同一资格建立新会话；用户以刚设置的用户名密码走正常登录。V 收不到账号 ID、用户名、密码、恢复材料或 C 的业务内容。C 不为每次资格兑付回调 V。

正常注册只要求用户输入**一封**学校邮箱验证码；密钥、散列、挑战和持钥证明均由客户端后台完成。V 或 C 因结果未知而重试时，只能核对本方原操作，不能擅自换槽位。

## 4. 双方持久状态与不可变不变量

| 方 | 状态 | 可发生的转换 |
| --- | --- | --- |
| V 每精确邮箱 | `FREE`、`RESERVED(slot, pk, ticket)`；退役待办期间附加 `RETIRE_PENDING(slot)` 锁 | `FREE → RESERVED` 仅在本次 OTP 成功且持久提交后；**当前 slot 全局唯一，已释放／退役 slot 不可重新签发**；V 调 C 退役前持久写待办并禁止旧槽位续票；收到 C 对**当前 slot**的退役或正式注销收据，原子 `RESERVED → FREE`；释放旧 slot 不影响之后的新 `RESERVED` |
| C 每槽位 | `ABSENT`、`ACTIVE(account)`、`RETIRED`、`CLOSED` | 开户时 `ABSENT → ACTIVE`；未开户资格取消时 `ABSENT → RETIRED`；旧号正式注销时 `ACTIVE → CLOSED`；后两种状态不得回到 `ABSENT` 或重新开户 |

C 的待开户意图不构成槽位占用，不能因别人创建了意图就阻止真正持 `sk_boot` 的用户注册。开户与退役若并发，必须由槽位唯一约束及事务序列化选出唯一结果：开户先提交，退役不得关闭该账号；退役先提交，旧资格永远不得开户。正式注销的 `CLOSED` 记录也拒绝旧资格。C 在正式关闭事务即清除槽位→旧账号的在线关联，但必须保留**与账号脱钩、至少含槽位和终态的拒重放记录**。票据有界不代表终态可按票据 TTL 删除：恶意或失陷的 V 仍可能对旧公钥／槽位签当前窗口的新票，C 必须长期保留最小 `RETIRED/CLOSED` 终态拒重放记录，直至另有经过审计的全局槽位淘汰机制。

同槽位只会合法产生 RETIRED 或 RELEASED 一种用途；V 检出不同用途收据或未知映射时不 ACK、不清新配额，进行事故核对。V 在释放配额后清除在线的邮箱→旧槽位映射，但保留不含邮箱的已处理收据／已用槽位标记，以便同一退役／释放重试获得幂等结果，而不能清除新槽位。两侧的历史日志和备份可能仍含旧映射，必须有明确保存期限；长期拒重放记录也须计入隐私与存储评审，不能宣传“注销后所有系统立刻忘记旧槽位”。

## 5. 未消费资格中断与私钥丢失

客户端仅在仍持有本次 `sk_boot` 时可继续原资格。V 返回原资格、客户端却已丢失 `sk_boot` 时，持钥证明必然失败，不能让 V 直接为同一邮箱换发新槽位，也不能仅因资格、挑战或 OTP 超时就放配额。

用户重新完成一次校邮 OTP 后，客户端生成**新** bootstrap 密钥和新槽位；V 先持久记录按旧槽位唯一的退役待办，阻断对旧槽位的任何续票，再对当前保留的旧槽位签发固定格式取消授权并调用 C。C 验 V 授权，并原子尝试 `ABSENT → RETIRED`；只有终态与 receipt outbox 同事务提交后才签发退役收据；签名尚未就绪时为 `202 RECEIPT_PENDING`，不返回可释放收据。若旧槽位已 `ACTIVE` 或 `CLOSED`，C 不退役、不提供旧账号资料，V 不签发新资格；用户应走旧号登录或独立恢复。若 C 退役成功而收据回包丢失，V 保留旧槽位及待办并用相同旧槽位重试取得同一已提交终态收据；待办期间既不签旧票，也不开放新资格。

V 只在收据验签且与该精确邮箱的**当前**旧槽位相等时，原子清除旧占用；然后在此次新 OTP 会话仍有效且用户已提交新 `pk_boot/slot_id` 时签发新资格，否则要求重新收码。V 必须先完成旧槽位退役再签新资格。恶意 V 可滥用取消授权阻断尚未开户的用户，这属于其已有的拒绝服务能力；取消授权**不能**关闭已开户账号或成为密码重设凭据。恶意 V 还可主动试探 C 是否肯对某邮箱当前槽位出具退役收据，从而推断该资格是否已开户；C 不返回账号 ID、用户名或内容，但不能宣称 V 对“是否完成注册”也一无所知。

## 6. 七天注销与配额释放

申请注销时，C 用当前账号的独立控制凭据完成要求的再次认证，进入七天缓冲；尚未公开的后台发布任务自申请事务获胜起不再公开，不能靠已撤销会话在缓冲期继续发布。C 用实际数据库时间确定 `due_at`；只有在账号行持锁后以新采样的实际时间仍早于 `due_at` 的主动成功登录或新封禁可撤销申请，请求发起时间不算。到期后即使关闭 worker 延迟，账号也立即停止认证、恢复和业务写入，状态页显示“正式关闭处理中”；迟到登录或封禁不得取消申请。关闭事务再按账号版本与并发次序裁决并生成释放事件。没有确切的旧号不可逆关闭结果，C 不得生成可外发的释放收据。

到期事务在同一持久提交中将账号永久置为关闭、撤销会话、将槽位置为 `CLOSED`，并写入唯一的待签／待投递释放事件。若签名由 HSM 或外部服务完成，不能假设它与 SQL 事务天然原子；**事务提交后**才依据已提交的关闭事实签发固定 `RELEASED(slot)` 收据并投递。签名或投递失败只让资格保持“释放处理中”，绝不能先放开 V 配额；后台按同一槽位幂等重试。受限注销状态页可在收据已签发后取同一收据，供用户再次收码时转交 V；页面权限不提供旧号恢复或社区内容。

V 验 C 全局公钥、作用域及签名，仅当收据槽位等于该精确邮箱的**当前**槽位时原子释放。对已经处理的旧槽位重复收据只返回原处理结果，不能清除后来的新槽位。V 不能因七天到了、C 暂时不可用、传输超时或管理员要求而自行放开配额。重新注册必须重新收码、新生密钥与槽位，C 新建账号不继承旧身份、内容、禁言或会话。

## 7. 故障、轮换与隔离

| 场景 | 必须观察到的结果 |
| --- | --- |
| V 提交保留后响应丢失 | 十分钟内复用原确认幂等键，不重新收码；之后重新验证 OTP，仍持旧私钥则取得同一槽位／公钥的有效资格，私钥丢失走第 5 节退役 |
| C 建号后响应丢失／重复证明 | 只有一个账号；已用资格和挑战不再给会话，用户用用户名密码登录 |
| 用户名冲突／C 待开户意图过期 | 未消费槽位；同一资格与私钥可建立新意图，不能直接重发旧证明 |
| 退役与开户并发 | 只有一个事务成功；`ACTIVE` 不能被退役，`RETIRED` 不能被开户 |
| 正式注销与主动登录取消／封禁并发 | 持锁状态转换发生在 `due_at` 前才能取消；到期后即使 worker 尚未提交也拒绝登录／恢复／业务写入，只在真正 `CLOSED` 后出现释放收据 |
| C→V 释放或退役投递失败 | V 保留旧占用并重试；用户看到“资格释放处理中”，不允许第二个槽位 |
| C 已提交退役而 V 未收到回包 | V 已持久登记的待办阻止旧槽位续票；重试同一退役授权直到取得 C 收据，再比较当前槽位原子释放；不能因新 OTP 到期而取消待办 |
| 退役待办与正式注销释放并发 | `RELEASED` 若先到，V 按当前槽位及版本原子释放并终结同槽位退役待办；随后 `SLOT_NOT_RETIRABLE` 不得恢复配额或影响新槽位 |
| 旧退役／释放收据重放 | V 只对旧槽位返回幂等结果，不释放当前新槽位；C 的旧资格也因终态记录不能再开户 |
| V 或 C 恢复旧备份 | 冻结 V 发码确认与配额操作，以及 C 全部认证、受保护读取和写入；旧快照会话一律拒绝并撤销。利用不可回滚的已提交事件／对端状态及单调密钥撤销记录核对账号、槽位、凭据版本、会话和受信签名钥后再开放；不能把 `CLOSED/RETIRED` 恢复成 `ABSENT/ACTIVE`，也不能把 V 的新占用或已撤销密钥退回旧状态 |

测试、预发布与生产必须使用互不复用的 V/C 签名钥，受信 `key_epoch` 配置绑定唯一环境及预期对端，因本协议签名消息没有环境字段。例行 V 注册签名钥轮换只改变全局 `v_key_epoch`，不改变邮箱占用与槽位；未消费资格所需旧公钥须在受控窗口内继续验收，或要求用户重新收码取得同一槽位／公钥的新签名。C 退役／释放签名钥轮换不改变已提交终态和待投递事件；可基于同一终态用新钥重签同一用途与槽位。怀疑 V 注册私钥泄漏时，C 应立即停验该钥，受影响的未消费资格须重新收码；怀疑 C 收据私钥泄漏时，V 应停收该钥的退役／释放收据并由 C 以新钥重签。已经被伪造收据错误释放的配额不能仅靠换钥自动修复，须冻结、核对和处理可能的双号；但签名钥泄漏本身仍不能只凭校邮重置已有账号密码。

V 与 C 不共用数据库、备份、签名私钥、云控制面、请求 ID、幂等键或诊断账户。协议必要的 `slot_id` 与 `pk_boot` 两边均可见，故**两库合并可直接连接邮箱和账号**；持钥证明和散列绑定没有消除这一隐私成本。邮箱、密码、恢复码、完整资格、挑战证明和会话令牌均不得进入普通日志或分析 SDK。C 不接收邮箱；V 不接收私有用户名或账户材料。

## 8. 实施前审阅用不变量与待完成项

1. V 按精确邮箱串行化配额并对当前及历史槽位施加全局唯一／不复用约束；C 按槽位串行化开户／退役／关闭。所有操作在超时、重试、并发和灾备恢复后仍不得出现两个由**诚实 V** 对同一精确邮箱放行的有效账号。
2. C 只有在 V 签名、`slot_id = SHA-256(固定作用域 || 算法标识 || pk_boot)`、对真实 C 挑战的持钥证明、不可修改开户意图及槽位终态检查全部通过时才开户。恶意 V 用另一个公钥签用户的同一槽位应被 C 拒绝；V 用全新槽位伪造新资格仍可能成功。
3. 资格、退役收据、释放收据、旧会话和邮箱 OTP 不能成为已有账号登录或重设密码的替代路径；重复注册请求不得重发旧会话令牌。
4. 取消未消费资格与正式注销分别走 `RETIRED` 和 `CLOSED`；V 只凭对应 C 收据及当前槽位比较释放。旧槽位在 C 至少保留与账号脱钩的不可重用终态。
5. 恢复体验、密码基线和逻辑数据／接口已在[恢复决策](auth-privacy-recovery-decision.md)及[数据与 API 契约](auth-privacy-data-api-contract.md)细化；V/C OpenAPI和迁移设计已成稿，仍须审阅实际SQL／约束、验证移动端 WebAuthn 适配、落实 V/C 独立部署，并完成独立安全评审。**文档规格完成不等于获准开始生产认证实现。**
