# 认证隐私架构决策交接：交给 Codex / GPT-6

状态：2026-09-26。**本文件是历史任务说明；本轮用户随后确认了“每次注册都验证校邮，日常用户名＋密码登录，同一精确邮箱地址同时最多一个有效账号”。当前架构见[认证与隐私架构决策](auth-privacy-architecture-decision.md)。**
目标：让 Codex 中的 GPT-6 在当前分支既有设计基础上，重新评估 Hnuhole 的认证与匿名保护架构，给出可落地、可审计、适合 To C 产品的最终方案。

## 一、为什么暂停当前方案

Hnuhole 的核心卖点是匿名保护。当前 ADR 0005 已经确立“邮箱—账号不可由任何单一内部主体关联”的强隐私方向，但继续 grilling 后暴露出一个更根本的问题：

如果“邮箱验证码验证成功”本身就直接恢复或决定某个 Hnuhole 账号，而唯一邮箱验证方可以主动恶意伪造“验证码已通过”，那么该验证方可能绕过真实邮箱控制权，进一步尝试冒充用户、恢复账号或建立邮箱—账号关联。

因此当前需要重新决定：**邮箱验证到底应该是账号控制凭证，还是仅作为校园资格证明；账号真正的长期控制权是否应交给用户侧密码学凭证（如 Passkey / WebAuthn）。**

在本决策完成前，不继续实现认证主链。

## 二、已经确认且默认继续有效的产品规则

除非本次架构评审明确说明某条必须被替代，否则以下仍是当前规则：

1. 目标用户使用学校邮箱验证校园资格，当前后缀规则为严格的 `hainanu.edu.cn`。
2. 社区业务数据库不得保存邮箱原文、可解密邮箱副本或可直接反推邮箱的账号映射。
3. Hnuhole 社区侧不得让管理员、普通运营或单一内部主体看到“具体邮箱 ↔ 具体社区账号”的对应关系。
4. 正式注销后，同邮箱重新注册创建全新账号，不恢复旧身份、旧私信、旧收藏等账号状态。
5. 禁言允许申请注销；七天缓冲期内禁言继续，正式注销完成后禁言随旧账号终止，新账号不继承。
6. 封禁期间不能申请注销；缓冲期内新封禁会取消注销申请。
7. 同一移动账号会话当前按单设备使用；新设备接替旧设备。
8. 会话当前设计为 30 天有效，剩余 7 天以内且用户活跃时静默续期。
9. 不允许通过单方 HMAC、普通邮箱哈希、可解密邮箱副本或人工管理员查邮箱来冒充“隐私方案”。
10. 生产环境的隐私承诺必须明确安全边界，不能用模糊宣传代替实际威胁模型。

## 三、2026-09-25 至 2026-09-26 新增确认

这些是最近 grilling 已明确的约束：

- 稳定匿名标识若继续使用，必须限定在 Hnuhole 服务作用域，不能跨不同应用复用同一 pseudonym。
- 密钥轮换不能把已有用户变成“新用户”。
- 换机、卸载、清本地数据后的恢复方案不能偷偷依赖旧设备中一个用户不知道的长期秘密，除非本次架构明确把 Passkey / 同步认证器升级为正式账号控制凭证。
- 用户明确认为“单个验证方如果主动恶意伪造验证结果就可能造成泄漏/盗号”不可接受，需要重新评估。
- 用户明确是 To C 产品，不希望常规登录出现两个验证码等明显损害体验的流程。

## 四、当前候选架构（均未定案）

### 候选 A：原 ADR 0005 强化版

邮箱验证码仍是唯一登录凭证，使用独立邮箱验证方 + 社区方，配合盲签名 / OPRF / VOPRF / 门限密码学等构造稳定匿名凭证。

优点：
- 对现有产品规则改动小。
- 仍可维持“邮箱验证码唯一登录凭证”。

核心风险：
- 如果唯一邮箱验证方完全恶意并可伪造“验证成功”，需要证明系统如何防账号接管；如果做不到，必须明确降低安全承诺。
- 如果改成两个独立验证方，可能导致双验证码或更复杂的 To C 体验。

### 候选 B：匿名校园资格凭证 + Passkey / WebAuthn 账号控制

把“校园资格”和“账号控制权”分离：

- 学校邮箱验证：只证明“用户具有校园资格”。
- 验证方通过盲签名、Privacy Pass 类 token、匿名凭证、BBS+ 或其他经评审方案，发放不可直接关联的资格凭证。
- Hnuhole 创建账号时验证匿名资格，并绑定用户生成的 Passkey / WebAuthn 公钥。
- 后续账号登录依赖 Passkey / 用户侧密钥，不再依赖邮箱验证方直接恢复既有账号。
- 邮箱验证方即使主动恶意，理论上最多可伪造新的“合格用户”，但不能仅凭邮箱验证权接管已有账号，前提是恢复流程不回退成“单邮箱验证码即可重置 Passkey”。

优点：
- 更适合 To C：首次可能一次邮箱验证，后续可使用 Face ID / Touch ID / Windows Hello 等。
- 账号控制权不再长期掌握在邮箱验证方手上。
- 更容易把“资格证明”和“社区账号”做密码学隔离。

核心难点：
- 必须重新定义账号恢复。
- “邮箱验证码是唯一登录凭证”这条旧规则会被替代为“邮箱是资格根，Passkey 是账号控制凭证”。
- 需要明确同步 Passkey、恢复密钥、旧设备、设备丢失后的行为。

### 候选 C：学校官方 SSO / OIDC / SAML / CAS + 匿名凭证 + Passkey

如果学校提供可合法接入的官方身份系统，则由学校作为“校园资格信任根”，再通过 pairwise subject、匿名凭证或盲化层减少学校身份与社区账号的直接关联。

优点：
- Hnuhole 自己不能随意伪造“这是学校用户”。
- 资格来源更权威。

核心难点：
- 是否能获得学校官方授权和接口。
- 学校 IdP 可能天然知道用户正在访问 Hnuhole，需要明确隐私边界。
- 仍然需要设计社区账号控制权和恢复。

### 候选 D：ZK / DKIM / ZK Email 类资格证明

尝试让用户证明“我持有由可信邮件系统签名的某封学校邮件”或“我满足某个邮箱域属性”，同时隐藏具体邮箱。

优点：
- 理论隐私很强。

核心难点：
- 必须有一个 Hnuhole 无法自行伪造的可信邮件签名来源；如果只是 Hnuhole 自己发验证码邮件，再证明收到了这封邮件，并不能消除自身作恶问题。
- 实现、审计、移动端性能、依赖成熟度都明显更复杂。
- 不应该为了“听起来高级”而自行发明密码协议。

## 五、GPT-6 必须回答的问题

请不要直接写代码。先完成架构决策，并逐条回答：

1. **威胁模型**
   - 要防哪些攻击者：恶意社区方、恶意验证方、数据库泄漏、日志泄漏、单一运维人员、验证方与社区串通、客户端被盗、邮件服务商等。
   - 哪些攻击明确不在保证范围内。
   - “任何单一主体不能获得邮箱—账号映射”具体如何验证。

2. **账号控制权**
   - 账号最终由什么控制：邮箱验证码、Passkey、客户端私钥、匿名凭证或组合。
   - 邮箱验证方完全恶意时，能否接管已有账号。
   - 如果不能防，必须直说，不得用 OPRF / 盲签名术语掩盖信任假设。

3. **校园资格**
   - 如何证明用户是本校成员。
   - 邮箱验证结果如何变成社区可验证、但尽量不可关联的资格证明。
   - 是否需要盲签名、VOPRF、Privacy Pass、BBS+、学校 SSO 或其他方案。

4. **To C 用户体验**
   - 首次注册需要几次邮件操作。
   - 日常登录是否需要邮件。
   - 换机需要什么。
   - 丢设备后如何恢复。
   - 是否存在用户必须保管的恢复码。
   - 不接受常规登录长期依赖双验证码，除非明确证明没有更合理方案。

5. **恢复机制**
   - 这是本次设计重点。
   - 如果使用 Passkey，必须说明同步 Passkey、Passkey 丢失、所有设备丢失、Apple/Google 账号不可用等情况。
   - 如果恢复最终可以只靠一个恶意邮箱验证方重置账号密钥，则必须指出这会重新引入账号接管风险。
   - 给出恢复安全性与可用性的具体取舍。

6. **注销与重新注册**
   - 正式注销后必须是新账号。
   - 不得永久维护可直接查询“旧账号和新账号其实是同一人”的普通业务映射，除非有明确必要性和保留期限。
   - 旧公开内容仍按现有注销占位规则保留。

7. **密钥和作用域**
   - Hnuhole pseudonym / credential 不得跨其他服务复用。
   - 密钥轮换不能把原用户变成新用户。
   - 明确各主体分别持有什么密钥，谁绝不能同时持有什么。

8. **日志、幂等和侧信道**
   - 两个服务是否会因为请求 ID、幂等键、精确时间戳、IP、日志、消息队列、备份而重新变得可 join。
   - 给出可以真正执行的最小日志策略和故障排查策略。

9. **协议成熟度**
   - 优先使用已有标准和成熟库。
   - 不自行设计新的密码学原语。
   - 对每个关键原语列标准 / RFC / W3C / 主流库成熟度与实施风险。

10. **最终输出**
   必须给出：
   - 推荐方案；
   - 至少 2 个备选方案及放弃理由；
   - 端到端时序；
   - “谁知道什么”的数据视图；
   - 注册、正常登录、换机、丢设备、注销、重新注册流程；
   - 威胁模型表；
   - 数据库存什么 / 不存什么；
   - 密钥持有和轮换；
   - To C UX；
   - 需要修改的现有 ADR / accounts.md 规则；
   - 实施前必须完成的安全评审清单。

## 六、决策原则

- 匿名保护是产品核心，不为了快速开发而退回“邮箱哈希一下就算匿名”。
- 同时这是 To C 产品，不接受为了理论安全让普通用户长期承受明显反常的登录流程，除非没有更合理的工程方案。
- 若“强安全 + 单邮件操作 + 不增加长期用户凭证”三者无法同时成立，要明确指出不可能同时满足，并让产品层选择，不要伪造折中。
- 优先调整系统架构，而不是自己设计新密码算法。
- 本轮允许推翻“邮箱验证码是唯一登录凭证”，但必须说明为什么、影响哪些既有设计、迁移成本是什么。
