## 原因与实现

附件 `ad90fd8f7d1d350efa4d17e22777e065.mp4` 约8秒：提交后编辑器很快收起，正文等待约5秒才出现。原界面等服务端任务发布、客户端查到结果、再读取评论正文后才显示完整评论。服务端已有PostgreSQL持久任务和异步发布，默认worker轮次间隔2秒；客户端原来固定每3秒核对一次。录屏没有各阶段计时，不能把约5秒全部归因于数据库持久化。

- 本地加密任务保存成功后，立即以原文、原图片、实际发言身份和回复目标生成本人可见的第一条评论；网络提交和发布继续在后台进行。未改变先保存任务再发命令的可靠性边界，任务库失败时保留编辑内容、不发网络命令。
- 服务端确认发布后按真实commentId衔接和去重，本次新发内容保持首条位置；读取正文暂时失败会自动重读，不要求用户点成功后的刷新按钮。其他既有评论保持服务端快照顺序；没有把本人侧展示当作公开发布确认。
- 没有“发送中”、成功提示或成功后的手动刷新入口。取得真实commentId之前，远端点赞/回复等操作保持不可用，避免向任务ID误发评论操作。
- 明确失败撤回本地评论，并在页面顶部独立位置提醒“评论发送失败，可在系统消息中重试”；系统消息保留原文、图片、身份和回复对象。明确未接收的拒绝保留原输入恢复链路。网络超时/结果未知不冒充失败，也不重发创建命令。
- 近期待核对任务前8轮每500ms查询，接着8轮每1秒、后续每3秒，总计最多40轮；无待处理任务不持续查询，后台暂停，恢复前台重新核对。保持账号/授权窗口隔离和原命令幂等规则。
- 保留另一会话新增的 `_contextReadVersion` 及 `late context from before publication cannot regress count or ownership` 回归，防止旧上下文覆盖发布后的计数和本人操作权限。

本轮没有引入Redis、修改服务端事务或部署后端。Redis预写不能解决客户端必须等结果才展示的问题；本轮首先消除这段可感知等待。真实服务端各阶段耗时仍须在统一真机链路中测量。
