# Hnuhole 独立账号恢复与密码策略 v1

日期：2026-09-27；修订：2026-09-28。状态：**实施前产品与安全规格；未实现，未经过独立安全审计。** 本文补足[架构决策](auth-privacy-architecture-decision.md)和[注册协议](auth-privacy-registration-protocol.md)的旧号恢复规则。精确接口与持久约束见[数据与 API 契约](auth-privacy-data-api-contract.md)。

## 1. 决定与取舍

校邮 OTP 只给每次**新账号**签发资格，不能查询旧号用户名、登录或重设密码。注册完成前必须保存并确认一份由社区方 C 产生的高熵恢复码；注册完成后推荐用户另绑一个可同步 Passkey，Passkey **可选**，只用于旧号恢复，不替代已确定的用户名＋密码日常登录。旧号恢复全程只接触 C，不向 V 发送邮箱、槽位、恢复事件或通知。邮箱单独找回体验更简单，但会让恶意 V／校邮系统重新得到旧号控制权；Passkey 单独承担恢复则把平台同步和换机失权变为单点风险。

恢复码是**独立的单次使用账号控制凭据**，不是六位校邮验证码，也不是附加在密码上的第二因素。谁先取得未用恢复码，谁就可能抢先重设密码；Passkey 私钥或同步账户失控也会造成相应风险。密码、恢复码和所有备用 Passkey 均失去后，C 不做人工按邮箱配对或例外重置。此时原精确邮箱在 V 仍有活动槽位，用户也**不能凭重新收码注册第二个账号**；只有此前已合法关闭旧号并完成释放才可再注册。这是严格配额与防校邮接管旧号共同带来的实际代价，注册页须在保存恢复码前明示。

## 2. 注册时保存恢复码

1. C 创建短期待开户意图时用密码学安全随机数生成 **128 位**恢复秘密，按 RFC 4648 无填充 Base32 编为 26 个字符；界面可按组加连字符。C 对固定作用域 `HNUHOLE/RECOVERY/V1`、零字节和解码后的 16 字节求 SHA-256，待开户意图中只保存摘要，不持久保存原码。输入只忽略显示分组连字符与空格并统一 Base32 大小写；解码后必须重新编码为同一规范 26 字符（含末尾零填充位约束），其他变形不接受。摘要有唯一约束，以恢复码本身在 C 内定位账号，忘记用户名也不需要校邮反查。128 位随机秘密允许使用快速单向摘要；这不适用于用户自选密码。
2. 原码仅在创建意图的**首次成功响应**经 C 的认证 TLS 连接展示一次。客户端不得主动把它写入普通日志、分析 SDK、自动截图上传、剪贴板自动同步或 HTTP 缓存；同时提醒用户系统截图可能同步到云端。客户端建议写下或存入用户选择的安全管理器，不自动保存到 Hnuhole 云端。另起确认画面，隐藏原码后让用户完整重输；确认值须与 C 所存摘要相符，才可提交本次开户持钥证明并消费资格。客户端本地比对可减少误输，但不能代替 C 校验。
3. 创建意图响应丢失时，C **不重放恢复码原文**。客户端仍持本次 bootstrap 私钥和 V 资格，就重新创建意图，由 C 生成新码与新挑战；旧意图到期删除，不占用槽位。首次意图最长十分钟。若 bootstrap 私钥也丢失，走[注册协议第 5 节](auth-privacy-registration-protocol.md)的重新收码和未开户槽位退役；不能因丢码或超时直接放开邮箱配额。
4. 注册成功后恢复码长期有效，直到首次使用、主动轮换或账号正式关闭；它没有校邮 OTP 的五分钟寿命。可选 Passkey 在开户成功后立即引导绑定，绑定失败不撤销已建账号或恢复码。

## 3. 可选 Passkey

C 采用 WebAuthn 可发现凭据：受信的 Hnuhole RP ID／origin 固定配置，`userVerification=required`、`residentKey=required`、`attestation=none`；用户句柄是 C 新生成的随机非邮箱标识。C 校验 challenge 一次性、origin、RP ID、类型、UV、credential ID、签名及账号绑定；不以单纯设备解锁或客户端自报成功为准。Passkey 只用于恢复证明和凭据管理，不直接创建正常社区会话。首次绑定及增删须有当前会话并重新输入正确密码；仅持旧会话令牌不够。密码忘记时先以已有恢复码或 Passkey 完成第 4 节重设，再管理凭据。首版凭据算法采用 ES256；十条 Passkey 上限为资源评审基线，变更须经容量／客户端审阅。WebAuthn `user.id` 用随机32字节句柄，`user.name` 是该句柄的 base64url，`displayName` 固定为“Hnuhole account”，不把私有登录用户名送到同步服务商。C 只存必要公钥、凭据ID、随机句柄及计数／备份状态，无 attestation 或真实姓名。

同步 Passkey 可以改善换机后的可用性，但用户的系统或同步服务商可能看到 Hnuhole 凭据的存在，且其同步账户的恢复能力影响 Passkey 安全。绑定界面用普通话说明这个隐私取舍；不把 Passkey、恢复码或用户名交给 V。Passkey 服务不可用时恢复码仍可用。此用法参考 [W3C WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/) 与 [NIST 同步认证器说明](https://pages.nist.gov/800-63-4/sp800-63b.html)，不宣称 Hnuhole 已获得任何认证等级。

## 4. 忘记密码、忘记用户名与轮换

1. 找回入口选择“使用恢复码”或“使用 Passkey”。有效恢复码的摘要在 C 内定位旧账号；可发现 Passkey 在完成有效 assertion 后以随机用户句柄定位旧账号。**先证明凭据，才显示私有用户名或账号状态**；无“输入校邮查用户名”接口。无效、已用、已关闭账号的对外失败提示一致，受多维限速控制。
2. C 校验凭据后建立最长十分钟、仅可**设置新密码**的受限重设意图，并一次性展示新生成的 128 位恢复码。旧恢复码在该意图内暂时保留为待消费，不能据此取得普通会话；若首次响应丢失，重新证明旧码或 Passkey 可建立新意图。**初步验码或验签不能预先授权创建意图**：C 取得账号锁后，须核对证明所见的凭据版本仍是当前版本，且所用恢复码摘要或 Passkey 凭据仍有效；版本或凭据已经变化就拒绝并要求全新证明，绝不能用旧证明记录新版本。创建新意图时 C 才在同一锁下递增**重设意图代次**、原子标记原意图废弃，并把唯一活动意图指向新意图；旧意图即使尚持相同凭据版本也不能再提交。最终重设同时核对统一凭据版本、活动意图 ID／代次和有效期，同账号并发只有一方成功。用户设置新密码并再次确认新码时，C 在同一事务里更换密码验证值、烧掉旧恢复码、激活新恢复码、**撤销所有旧 Passkey 和会话**并消费意图、递增凭据版本。无论本次使用恢复码还是 Passkey，另一种旧凭据也一并作废，避免被盗的备用凭据再夺回账号；用户以新密码登录后经新鲜密码复验重新登记 Passkey。已签发但尚未提交的旧 Passkey assertion／重设意图，以及并发的凭据管理请求，都必须因版本或意图代次不符而失败。重设成功**不自动登录**，用户以新密码正常登录；提交成功但响应丢失时优先用原提交幂等键查询不含秘密的结果。若账号正处于注销缓冲期，直接用新密码主动登录会取消注销，客户端须明确提示；其他情况下可用新密码登录核对，不重放旧码或旧会话。
3. 仍记得密码但丢了恢复码时，已登录用户经**新鲜密码复验**可换发新码；新码展示一次并确认后才原子替换旧码。若忘记密码，使用剩余的已登记 Passkey 先重设。新增、移除 Passkey 和更换恢复码不能只凭会话；每次正式凭据变更均须在同一事务中校验并递增统一凭据版本，使先前建立的重设意图和管理挑战失效。不能移除最后一个有效恢复途径而仍宣称账号可恢复。正常会话可在设置页查看本账号私有用户名，但不能查看旧恢复码原文。轮换恢复码采用十分钟的创建／确认意图，新建原子替代旧轮换意图；Passkey创建和删除的管理意图五分钟。各意图绑定证明时统一版本、当前会话和固定操作目标，最终锁内再次核对后提交；删除用先建意图、再带 Credential-Change-ID 的无体 DELETE。普通轮换码／增删 Passkey 递增统一版本只使旧证明和意图失效，不废止仍保留的其他凭据。精确路径见[C OpenAPI](../../packages/openapi/community-auth-api.yaml)。
4. 密码重设不是“主动登录”，**不自动撤销**七天注销申请；若仍在缓冲期，用户随后用新密码主动登录才依现有规则取消。正式 `CLOSED` 的账号不接受任何找回；禁言／封禁状态及旧内容归属不会因密码重设改变。

## 5. 密码、滥用与通知

密码用于单因素日常登录：至少 15 个 Unicode 码点，至少支持 128 个码点，允许空格和粘贴；统一 NFC 后计数和验证，不截断，另设输入字节上限防资源耗尽。无需大小写／数字／符号组合要求，不强制周期更换；创建及重设时用常见、泄漏和与用户名相关的弱密码阻止名单。按 [NIST SP 800-63B 密码要求](https://pages.nist.gov/800-63-4/sp800-63b.html)取此基线。C 存每账号独立 16 字节盐的 Argon2id 验证值及参数版本，初始评估基线为 RFC 9106 的内存受限配置 `m=64 MiB, t=3, p=4`、32 字节输出；上线前按真实机器的延迟、内存和并发压力校准并限制 KDF 并行工作数，不能默默降成快速散列。[RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html)、[OWASP 密码存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

用户名密码登录、恢复码尝试、Passkey challenge、注册意图和凭据管理分别做按账号／凭据、网络来源及 V/C 各自可见设备信号的限速与异常检测；不让攻击者靠错误输入永久锁住无辜账号。不存在的用户名采用同形错误和受控的等价计算路径，不能通过响应、时延或限速明显枚举；具体阈值须在容量测试与独立评审中定值。密码重设、恢复码轮换和 Passkey 变更写入 C 的受限安全事件并尽力通知此前绑定的设备；无独立联系地址且不向 V 报告恢复事件，因此丢失全部设备时**无法保证异地通知**，不能宣称满足 [NIST 账号恢复通知要求](https://pages.nist.gov/800-63-4/sp800-63b.html)。通知不含恢复码、用户名、槽位或内容。[OWASP 找回指南](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)作为统一响应和限速参考。

## 6. 审阅门槛

- [ ] 走通“恢复码有、用户名忘”“新机有同步 Passkey”“旧码／Passkey 被盗”“全部凭据丢失且邮箱槽位仍占用”“C 响应丢失”“并发重设”“注销缓冲内重设”场景；对每种只出现一个账号与一份当前恢复码。
- [ ] 验证恢复、凭据管理、通知、日志、截图与备份不把邮箱送入 C，也不把恢复事件送入 V；Passkey 的 RP ID／origin 与移动端桥接方案通过专项安全审阅。
- [ ] 用户测试确认保存恢复码、全部丢失的真实后果与可选 Passkey 的同步隐私提示可以被普通用户理解；参数和通知能力上线前复核。
