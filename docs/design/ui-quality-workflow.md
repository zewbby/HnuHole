用户要求把frontend-design安装到项目并建立有质感、减少AI模板感的UI流程。项目入口为[hnuhole-ui-craft](../../.agents/skills/hnuhole-ui-craft/SKILL.md)，来源与固定版本见[项目技能记录](project-ui-skills.md)。本节具体化下方历史流程，不推翻已定业务、逐张评审或用户配色决定。

### 设计标准

HnuHole的页面以中文内容阅读和操作为主。质感来自字体、行距、对齐、可辨的表面层级及稳定反馈；不要用渐变、玻璃、噪点或发光替代设计。配色遵守用户最新页面指令，让内容先被看见；一处明确视觉重点足够，其他区域安静。具体色值仍按页尝试，不宣称全局定稿；栖息感由安静、包裹的表面层级表达，不自动添加装饰树枝或森林背景。

不套营销网页hero、feature-grid、证言、巨大标题或空泛副标题。不要所有项目都塞进相同圆角卡片；需要边界时才用表面、分隔或描边。中文字体优先实际覆盖完整的系统无衬线，用字重和行距形成细腻层级，不照搬英文展示字体。别为追求独特发明陌生控件或改变已确认的发布流程。

### 每页执行顺序

1. **读规则与看图**：读HANDOFF、当次计划、页面模块、真实图稿；记录正式／历史／缺失及文字规则更新。当前详情深色v2可参考，编辑、确认、列表、“我的”仍需新稿。
2. **确定用户任务**：这页让用户读、选还是提交？确定首要内容、当前状态、返回路径。完整产品设计与代码切片启用范围分开，不能把图中未来功能登记为实现，也不能因代码片较小删去用户要求的设计。
3. **检索并筛选**：frontend-design负责视觉观点；ui-ux-pro-max负责针对性移动端／Flutter检索；Impeccable的Operate／Read参考和critique负责审查。建议必须解释为何适合本页，推荐输出不能变成产品决定。检索若仍偏营销或无匹配，如实弃用，不persist成设计系统。
4. **内部设计卡**：写一个视觉重点，少量命名色、中文字体／字重／行距、间距尺度、布局和状态。助手自主决定初稿，不让用户先改prompt。字体未安装时使用可用fallback，避免图里漂亮但无法实现。
5. **PNG出图**：默认每轮一页一状态；用户指定一组多状态时按其批次执行。402×874为现有逻辑基准，必要时2倍导出。无手机外壳、图外说明和海报标题；真实中文内容验证长标题／昵称。新建或编辑位图使用imagegen；精确布局、手势和Flutter验收用实际渲染与截图，两种证据分开。用户已确认布局而只要求换色时保持结构，分别记录确认范围。
6. **看实际输出再修**：按[评审表](../../.agents/skills/hnuhole-ui-craft/references/review-sheet.md)检查文字、结构、内容、状态、匿名和噪声；一次集中修正后复看，避免无目的无限微调。图像生成的中文、图标、几何可能出错，不能只看prompt宣称成功。
7. **交图与版本**：输出实际图，简要解释主设计和待验项。新稿保存在`docs/design/ui-drafts/`、每页小型记录在`docs/design/ui-reviews/`。用户完整确认页面后登记并继续下一张；只确认布局并要求换色时继续本页配色，不能当作整页定稿或自动改全局色彩，不覆盖旧稿。
8. **落到Flutter**：把确认的布局映射到语义token及独立组件，校准实际截图；测试小屏、大字、键盘、安全区、读屏、按压和返回位置。PNG不代表业务接口、持久状态或授权通过，验收仍映射模块台账。

### 复审如何做

先检查行为与内容：保存失败有没有保留输入、未知结果有没有冒称失败、身份选择是否被误画成已绑定。再检查信息层级和阅读：中文行距、换行、对齐线、作者区是否压过正文。最后检查视觉：删掉一项没有明确用途的装饰，统一控件职责和状态色。具体缺陷写位置、用户影响和修复，不输出“高级感95分”等不可证评分。

针对普通正文／次文字实际测量对比度，触控区域按平台验证；未测量写NOT_RUN。画面质量、用户定稿、Flutter实现与设备通过是不同状态。完整Impeccable运行时／浏览器hook不属于PNG工作流必需项，本轮没有运行或下载。

2026-09-20 用户指定：后续 UI 工作同时使用 `ui-ux-pro-max` 与 `frontend-design`；已定稿页面若发现严重质量问题，可以在后续重画。本轮仅确定工作流程，未对历史页面完成全面审计，也未改变其确认状态。

用户进一步明确：只要其同意当前图定稿，助手应在同一轮同步定稿记录并直接开始下一张，不再等待额外的“下一张”指令或询问是否继续。每轮仍只新增一张待评审图；新图未经用户同意不自动定稿。真正影响业务的缺口仍先核对历史，必要时再提问。

## 当前配色探索方式（优先于旧配色约定）

- 2026-09-21：用户明确认可[长按对方文字 H](../../UI产品图/私信聊天-长按对方文字-配色H-v1.png)的黑灰＋低饱和蓝灰，要求“纳入色彩考量”。该套进入候选池，未锁定全局主题；下一张仍必须换色。方案参考值：背景 `#111214`、普通收到气泡 `#282C31`、本人气泡 `#3A414A`、选中气泡 `#A3AFBE`、深色字 `#17212D`、菜单 `#24282E`。色值属于设计目标，后续实现须从最终选定方案校准。
- 用户认为旧冰蓝主题 AI 感过重，要求参考成熟产品，保留黑底方向；不继续围绕同一旧页单独换色比较，而是正常推进下一张新页面，每张主动尝试一种不同配色。
- 配色变化应是一套完整、协调的搭配（背景与表面层级、主次文字、强调色及状态色），不只是随机替换按钮颜色；保持已确认业务、布局规律、字号层级、图标语言和操作逻辑，不借试色重开业务访谈。
- 用户明确否决仅改变小图标而主体仍近乎全黑灰的试色。后续配色须在真实功能区域形成一眼可辨的色彩层级，例如状态容器、信息卡、选中态或主操作；不能将“只换一个图标”宣称为整套配色。只读页面不为展示颜色硬加按钮，仍须保留黑底并保证可读性。
- 用户也明确否决私信正常页的酒红＋米杏＋玫瑰色组合，认为花哨。不能将“颜色可见”理解为来源栏、双方气泡、输入区各自大面积上不同颜色；后续优先中性黑灰底与单一协调强调色，在实际操作或消息区域体现，避免多处争夺注意力。该反馈不等于用户已认可某个新的色值。
- “页面定稿”和“全局配色定稿”独立记录。用户对某张图说“可以／定稿／下一张”只确认该页，不能推定为最终全局配色。直到用户明确认可并要求色彩定稿，才将该套配色用于之后全部页面。
- 每次记录试配方案与页面，避免重复试同类冰蓝搭配；不要求用户每轮选色，不必交付色板或 prompt。
- 全局配色确定后，可在后续统一重构旧图，保留旧版本，不擅自一次性重画全部已确认页面。旧页业务与结构不因换色自动失效。
- 已停止“申诉结果未通过”单独换色试稿的等待／交付；它不是已交付或已认可方案。下一张继续“私信举报：选择原因”，使用新的试配色。

## 每张图的流程

1. 先读交接、页面所属业务模块和已确认图稿，核对历史决定。当前按上方配色探索方式逐页试色，不再锁定旧冰蓝；全局配色确认后才统一沿用。
2. 用 `ui-ux-pro-max` 检查信息结构、入口可发现性、操作与返回路径、可读性、触控、安全区及状态反馈。新页面按技能要求检索设计系统建议，具体问题用最小范围的定向查询；只采用与本产品和平台相符的结果，不推定尚未选择的技术栈。
3. 用 `frontend-design` 形成简短内部设计方案：复用或明确颜色、字体层级、对齐和间距，以结构草图确认主次；检查布局与文案是否服务当前业务，去掉无意义的装饰、标签和重复信息。用户已确认的视觉方向优先于技能的风格偏好。
4. 出图前检查方案，出图后检查实际画面。继续一次一张 PNG、先自主设计再让用户微调，不附 prompt，不要求用户先确认文字方案；生成或编辑位图时使用 imagegen。
5. 用户确认后同步图稿状态。若涉及业务行为变化，更新所属模块及必要依赖；仅展示调整明确记录业务不变。真正缺失的业务决策核对历史后再提问，不能借质量检查重复访谈。

## 已定稿页面的复审与重画

- 优先处理影响阅读、入口发现、身份理解、操作结果或误触风险的问题；明显破坏跨页一致性和信息层级的问题也可列入后续重画。
- 每个问题记录具体页面／版本、可见证据、用户影响、建议及优先级。不凭“技能不喜欢这个风格”推翻用户决定，不虚构评分或检查结果。
- 复审发现问题不自动撤销原定稿。后续重画保留旧版，用新版本交用户评审；未经确认不替换定稿，不扩大功能范围。
- 通用建议与已定业务冲突时，先指出冲突及影响，不擅自增加草稿保存、二次确认、通知分类或更改已读规则。

## 静态图的验证边界

PNG 可检查排版、文案、视觉层级与可见状态，不能证明实际触控区域、读屏语义、焦点顺序、键盘避让、动态字号、横屏或动画已经可用。这些项目记录为原型／实现阶段待验证，不能标记通过。

实现阶段按平台检查触控区域（iOS 至少 44pt、Android 至少 48dp），不得把导出图片像素直接当作实际控件尺寸。正文及普通次要文字对比度目标至少 4.5:1，大字及有意义的非文本控件至少 3:1；需基于实际颜色及合成背景测量，不能凭肉眼宣称达标。技能中的矢量图标建议适用于产品素材，不改变当前 PNG 图稿交付方式。
