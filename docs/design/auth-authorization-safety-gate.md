# Authorization Safety Gate：可信时间与灾备授权门禁设计

日期：2026-09-29  
状态：**设计草案，待第 39 轮少量需求确认；未实施。**

## 1. 目的

本设计定义 Hnuhole 认证系统的第 0 步：在继续实现用户名密码登录、完整会话管理、恢复码、Passkey、七天注销和 Flutter 接入之前，先建立统一的 **Authorization Safety Gate（授权安全门禁）**。

它不是单纯的“可信时钟组件”。它回答的是：

> 当前这个实例、这份数据库状态、这个恢复代次，是否仍有资格产生、延长或继续承认有效权限。

现有注册链路已经可以产生账号、恢复码和初始会话，因此第 0 步必须先保护**已经实现的注册授权点**，再让后续登录、会话、恢复和受保护业务全部复用同一门禁。

## 2. 背景与当前缺口

当前隔离认证切片已完成：

`校邮 OTP → 校园资格 → 注册确认 → 创建账号、恢复码和初始会话`

现有实验实现和报告明确保留以下缺口：

- 可信 UTC / 时间高水位尚未实现；
- 时钟回退向量仍跳过；
- SQL 单调约束无法抵抗整库旧快照恢复；
- 真实独立授时、证据存储、灾备恢复和运营演练仍属于生产验收；
- 后续登录、会话到期、续期、封禁、注销截止都将依赖可信时间。

因此不能直接假设 `clock_timestamp()` / `now()` / 宿主机墙钟永远正确。

## 3. 核心安全目标

### GATE-01：授权时间不可静默倒退

用于安全裁决的时间必须满足：

`trusted_now >= persisted_high_watermark - allowed_skew`

超过允许误差的回退不得通过 `max(now, watermark)` 静默掩盖，而应进入 `FROZEN`。

### GATE-02：冻结是持久权威状态

冻结不得只保存在进程内存中。服务重启、进程切换和普通副本切换不能清除冻结。

### GATE-03：恢复代次单调递增

维护持久 `authorization_generation`。任何明确的灾备恢复、旧快照恢复后的重新放行或其他需要整体废止旧授权证明的安全恢复，都必须推进代次。

旧代次创建但尚未最终提交的授权命令，不得跨代次完成。

### GATE-04：证据有明确有效期

门禁必须基于可验证的时间/恢复证据，并记录 `evidence_valid_until`。证据过期后不能继续产生或延长权限。

### GATE-05：最终授权事务内重新检查

HTTP 入口检查不构成最终授权。任何会产生、延长、恢复或继续承认权限的数据库事务，在最终权威提交点必须重新检查：

- `gate_state == OPEN`
- `authorization_generation == expected_generation`
- 时间证据仍有效
- 当前可信时间未发生不可接受回退

以防止 TOCTOU：请求通过入口后、事务提交前发生冻结，旧请求仍获得权限。

### GATE-06：冻结前开始不等于冻结后可提交

Argon2、票据验证、PoP、外部计算等都可以在冻结前开始，但如果最终提交点已冻结或代次变化，必须拒绝产生新权限。

已经在冻结前完整提交的历史事实不倒滚。

## 4. 建议的权威状态模型

逻辑上至少需要：

```text
authorization_gate
------------------
singleton_id
gate_state                 OPEN | FROZEN
authorization_generation   uint64
trusted_high_watermark     timestamptz
evidence_version
evidence_issued_at
evidence_valid_until
freeze_reason
frozen_at
opened_at
```

实际字段、签名证据和生产存储可在实现设计中调整，但不得削弱上述语义。

### OPEN

允许在最终裁决点检查通过后产生/延长权限。

### FROZEN

系统认为当前授权时间、数据库恢复状态或可信证据不足以安全继续授权。

FROZEN 必须 fail closed；具体哪些“已有权限的只读请求”仍可继续属于本轮待确认项。

## 5. authorization_generation 的语义

这是**授权代次**，不是单纯 DR generation。

可能推进代次的事件包括：

- 灾备恢复旧数据库快照后重新开放；
- 严重可信时间异常后的人工/自动受控恢复；
- 需要整体废止冻结前 pending authorization command 的安全恢复；
- 后续安全设计明确要求的认证域重建。

它不应因为普通进程重启、普通部署或正常授时刷新随意变化。

任何授权命令在前置阶段获得的 `expected_generation`，最终提交时必须与当前代次一致。

## 6. 第 0 步必须先接入的现有注册路径

当前已实现注册链路必须在本切片内先接入 Gate：

1. 资格/票据只读解析可以发生在 Gate 之外；
2. `CreateSignupIntent` 是否允许建立短期意图由实现阶段进一步区分，但不得因此获得账号/会话权限；
3. `CommitSignup` 创建账号、恢复码和初始会话的事务必须在最终提交前检查 Gate；
4. Gate 冻结或代次变化时，不得创建账号、slot ACTIVE、恢复权或初始 session；
5. 原幂等键与永久 tombstone 规则继续有效，不能因冻结切换允许迟到请求重新获得权限。

第 0 步完成后重新跑现有 28 个数据库集成案例，并新增时间/灾备门禁案例。

## 7. 后续消费者

同一 Gate 必须被后续全部权威授权路径复用，不允许每个 endpoint 自己实现一套时间判断：

- 用户名密码登录；
- 新设备接替；
- 当前会话授权；
- Session 恢复；
- Session 静默续期；
- Session revocation 的状态裁决；
- 恢复码 / Passkey 密码重设；
- 恢复凭据管理；
- 七天注销申请、取消、FINALIZING 与 CLOSED 转换；
- 受保护读写；
- **业务写事务的最终授权点**。

OpenAPI 现有 `503 SERVICE_UNAVAILABLE` 已把“授时或灾备核对未就绪”纳入失败语义；实现时须统一映射，不把冻结伪装成 401/403。

## 8. 统一授权时间接口

认证/授权代码不能直接自行使用 `time.Now()`、`now()` 或 `clock_timestamp()` 作为最终安全时间。

建议抽象为类似：

```go
type AuthorizationDecision struct {
    TrustedAt   time.Time
    Generation  uint64
}

type AuthorizationGate interface {
    Snapshot(ctx context.Context) (AuthorizationDecision, error)
    RecheckForCommit(ctx context.Context, tx pgx.Tx, expectedGeneration uint64) (AuthorizationDecision, error)
}
```

具体 API 可调整，但必须表达：

- 可信时间；
- 授权代次；
- OPEN/FROZEN；
- 证据有效性；
- 最终事务复核。

## 9. 多副本语义

任何一个有权发现“全局不可信状态”的实例触发冻结后，其他副本不能继续产生新权限。

不能依靠：

- 进程本地 bool；
- 单实例内存缓存；
- 每副本独立高水位；
- “下一次刷新大概会同步”。

普通缓存可以用于性能，但最终授权必须以权威持久状态为准。

## 10. 旧快照恢复语义

数据库旧快照可能同时恢复：

- 较早的 `trusted_high_watermark`；
- 较早的 `gate_state=OPEN`；
- 较早的 `authorization_generation`；
- 当时仍有效、现实中已经过期/撤销的 Session。

因此**数据库自身保存的 OPEN 不能单独证明恢复后仍可信**。

生产设计必须有数据库快照之外的独立恢复证据/锚点，使旧快照恢复后无法仅凭快照内状态自动开放授权。

隔离环境可以用可控的模拟独立证据证明状态机与失败语义；这不能替代生产部署验收。

## 11. Freeze 与恢复原则

### Freeze

遇到无法证明授权时间/恢复状态可信的情况，进入 FROZEN，并持久记录原因。

Freeze 是安全事件，不应由普通请求、重启或普通健康检查自动解除。

### Unfreeze

必须是显式恢复动作，并满足新鲜可信证据与状态核对。

成功后：

- 推进 `authorization_generation`；
- 更新可信高水位；
- 记录新的证据版本/有效期；
- 再开放 Gate。

具体由谁/什么系统有权执行恢复，是本轮待确认项。

## 12. 必须验证的故障向量

第 0 步至少新增以下验收：

1. 墙钟在允许误差之外向后跳 → Gate FROZEN；
2. 时间/恢复证据过期 → 不产生或续延新权限；
3. 进程重启 → 冻结仍存在；
4. 多副本 A 冻结 → B 不能继续授权；
5. 恢复旧数据库快照 → 不能仅凭快照中的 OPEN 自动放行；
6. generation=N 的 pending 请求在恢复后 generation=N+1 → 不能提交；
7. 登录未来完成 Argon2 后、最终事务前冻结 → 不签发 session；
8. Session renewal 最终提交前冻结 → expiresAt 不变化；
9. 已有注册资格在 `CommitSignup` 最终事务前冻结 → 不创建账号/恢复码/session；
10. 冻结期间旧 Bearer 至少不能产生新的持久权限；
11. FROZEN 后取得新鲜可信证据 → 必须经过显式恢复才能 OPEN；
12. 恢复后旧 pending authorization command 全部因代次/重新检查失效；
13. 已在冻结前完整 COMMIT 的历史事实不回滚；
14. Gate 查询/刷新失败 → fail closed，不偷偷退回本机墙钟；
15. 旧幂等请求在冻结/恢复后不能绕过当前 Gate。

## 14. 本轮需要用户确认的产品/运营边界

以下问题不能仅由代码作者擅自决定。当前建议写在第 39 轮 grilling 中，确认后更新本文为 accepted。

### Q1：FROZEN 时已有登录用户还能做什么？

推荐：**所有需要认证的社区读写都 fail closed；只保留完全公开/无需账号的内容、健康检查和受限状态说明。**

理由：如果已经无法信任“这份快照里的 Session 是否现实中仍有效”，继续相信旧 Bearer 做认证读也可能泄露私有数据。

备选：允许认证只读、禁止写和续期。体验更好，但旧快照恢复场景下安全边界明显更弱。

### Q2：谁有权解除 FROZEN？

推荐：**不能由普通管理员按钮或单个 API 实例自行解除。必须由独立恢复流程在验证外部新鲜恢复证据后执行；生产至少要求受限运维角色 + 独立证据，完整权限方案后续部署阶段确定。**

隔离实现用测试签名/独立状态文件模拟，不把测试方式写成生产方案。

### Q3：允许的时钟回退误差是多少？

推荐设计值：**5 秒**。

小于等于 5 秒视为基础设施抖动，不触发安全冻结，但可信高水位不倒退；超过 5 秒进入 FROZEN。

该数值是工程策略而非密码学常数，生产应结合真实授时与数据库环境校准。

### Q4：可信证据最多多久不刷新？

推荐设计值：**5 分钟**。

超过有效期后停止产生/延长权限并进入安全不可授权状态。生产真实 TTL 最终由授时/证据机制 SLA 校准。

## 16. 完成定义

第 0 步完成不等于“增加 trusted_time 表”。

完成必须能够提供隔离验证证据证明：

> 已经实现的注册链路和后续统一授权边界无法绕过 Gate；时钟异常、证据过期、旧快照、多副本、恢复代次变化和授权途中冻结都不能产生新的有效权限。

生产独立授时、独立证据存储、真实恢复演练和人类安全审计仍须单独完成，不能由隔离测试替代。
