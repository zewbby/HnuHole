### 尚需补齐的接点

1. Redis client 是限流 Controller 的私有字段，当前没有通用快照存储接口。与公共接入统一约定快照装配方式，快照不经过限流计费 API 存取名单。
2. `infra/docker-compose.yml` 当前尚未加入 Redis 服务；现有交付提供 Redis 配置与启动操作说明。是否使用 Compose 沿用环境部署方式，需要 Compose 时由公共接入负责人统一补齐。
3. Redis 的 256 MiB 是开发示例，不是快照预算或容量承诺。快照须配置并测量自身字节预算、账号额度及限流预留，不能只增加 key 前缀。
4. 快照 ACL、命名空间、连接池、超时与配置版本应与限流分开，不能为了快照修改限流 policy、代次或恢复屏障。
5. 限流的持久准入协调、verified-db 降级和恢复屏障是计费业务语义，不直接套到快照。快照仍遵守不静默退回 PostgreSQL、不在丢失游标下重建名单的约束。
6. `community_comments_read.go` 中列表读取、创建、统计和清理之外，评论定位接口也直接读 `c_comments.snapshots`，必须一并迁移。

## 阶段二 快照一致性与发布设计

推荐 GPT-6 Astra，推理强度 `xhigh`。

- 定义 PostgreSQL/Redis 两种存储实现与快照版本、来源路由及游标校验方式；兼容旧签名游标和已有排序模式。
- 设计固定 30 分钟到期、每份 10,000 ID/字节上限、跨实例账号额度和模块总预算。Redis 原子操作需覆盖并发占额、创建、失败补偿、过期回收和预算核销。
- 明确 Redis 写入成功而 SQL 事务失败、Redis 写入响应丢失、授权撤销、并发重试和进程中断后的可见性与配额收敛。
- 明确短超时和统一的一次短重试预算，避免延长账号或授权锁持有时间。
- 固定无效游标、存储故障、账号额度、单份过大和模块预算满的接口约定。
- 设计先兼容读取、再统一开启 Redis 新建、至少 30 分钟过渡和明确开关回退。回退保留新限流协议和永久回执，不直接回滚到不认识限流围栏及关闭回执的旧二进制。

完成条件：关键并发与故障场景都有确定结果，预算不越界，失败不长期占额，游标丢失不静默重建。只为符合条件的架构取舍新增简短 ADR。

## 阶段四 客户端恢复和置顶衔接

推荐 GPT-6.1 Sol，推理强度 `high`。
