## 2. 三个候选的裁决

**Redis 全账本扫描和写回：优先定位，尚不批准跳过校验。** `commentsnapshot/write.lua:3,36` 在 Prepare、Publish 分别调用 `readLedger`；`ledger_v2.lua:59–84` 每次完整验证所有记录，检查重复 ID/请求、整数边界、时间/状态、所有者及累计预算。`save:91–109` 再构造并 SET 全账本；Publish 实际只改变目标状态字节。现有样本占用从 1024 增至 1384，每次约 211–285 KiB 账本。这是两个不同提交边界下的重复扫描，不可直接合并：Prepare 负责 SQL 提交前预留，Publish 必须在 SQL 成功后执行；中间可能有其他进程修改账本。

替换 Publish 的全量 SET 为局部状态修改也不能立即采纳：它只触及一个约 2.41 ms 的客户端段，而达标缺口为 3.62 ms；并且仍需证明高水位、账本过期、OOM 部分执行、ABORTING 及失败补偿等价。现有跨度没有拆分扫描与构造/写回，不能凭代码大小承诺收益。

**成功后 Abort：确有重复，但当前不作为本次修复。** `withIdentitySession` 和 `withPostSession` 成功 `CommitAuthorized` 后仍执行 defer Abort。`authorization_gate.go:375–410` 会忽略已关闭事务的 Rollback 错误，然后另开事务，重新锁 Gate 并核对外部锚点。现有注释要求失败事务必须 Abort，没有说明成功事务需要这次收尾。它是公共流程，两后端及其他模块都受影响。

只作离线反证，将每条原 HTTP 时长减去该条两个 Abort 后重新取最近秩 P95：PG 108.314 ms、Redis 125.395 ms，算术回退约 +15.77%；若仅减去 Redis Prepare/Publish，Redis 为 145.9559 ms，对原 PG 约 +3.77%。**这两组不是优化结果或验收结果**：删除跨度会改变队列、调度和尾部成员，不能据此预测修改后的 P95。它们只能否定“删公共耗时必然改善相对比例”和“某个短子段必然足够”的推断。

若以后要实施成功分支跳过 Abort，最小设计必须是显式 `committed` 标志，仅在 `CommitAuthorized` 返回 nil 后置真；失败、取消、panic、锚点已写而 SQL 提交失败仍须独立 Abort。不能依据 `ErrTxClosed` 跳过，因为失败提交也可能关闭事务。最终授权、会话续期和 SQL 提交顺序必须保留。成功后的 Abort 当前忽略错误，本来也不是拒绝已提交响应的权限判定；但它还承担较早落盘外部冻结的作用，删除后需证明失败事务自己持久化冻结、下一次 Snapshot/Commit 拒绝异常锚点，不能只证明“成功事务已关闭”。目前没有证据证明必须扩大到这个公共边界，所以本次不实施。

**评论投影重复查询：记录为后续候选，本次不批量改写。** `community_comments_read.go:262` 每次读作者；回复还读取目标评论身份和作者。请求内去重可减少查询，但全样本两后端投影均值几乎相同，优化还会缩小 PG 分母；不能据此推出 Redis 相对回退下降。缓存作者/目标也须保留最终事务内可见性和注销状态语义。

## 3. 唯一下一步：可证伪的 Lua 分段诊断

诊断 ID `P5-D1`。要检验的假设是：**Redis 两次创建 RPC 的主要可优化执行成本位于完整账本扫描，而非全量写回或客户端/服务端排队。** 预先将“主要”定义为：两次脚本的扫描总时长占各自脚本总时长的比例，至少 80% 的测量请求达到 70%。这是选择优化方向的诊断阈值，绝非修改 5% 产品验收门槛。

实施边界：从精确 4b 源码生成 D 盘诊断副本，只增加观测。正式源码的授权和存储逻辑保持不动；保存诊断差异、源码/脚本/API SHA。Sol/high 先交付可审查补丁和冻结协议，随后只在本任务一次性环境执行以下一个诊断。

1. 在诊断副本的 `commentsnapshot/ledger_v2.lua` 分别记录 `readLedger` 的 GET、完整验证循环及其余处理，`save` 的字符串构造与 SET，外层记录脚本总时长；仅给 Prepare/Publish 启用。脚本计时用 Redis TIME 的微秒差，仅用于脚本内部耗时；原业务 `now` 保持原一次取值，不能以诊断时间替换或延长 TTL/lease。
2. 诊断脚本成功返回独立 timing envelope，由诊断版 `redis.go:call` 校验并剥离后，把原返回数组原样交给业务代码。错误原样抛出，不增加 catch/retry、持久化键或公共响应字段。日志只写请求关联 ID、操作、记录数及耗时，不写令牌、payload、账号或 SQL 参数。所有诊断数据落 D 盘私有任务目录。
3. Go RAW 记录 Prepare/Publish 各自脚本调用跨度，连同现有端到端 RPC 和服务端总段保留；增补 PG 新建快照 DELETE/INSERT 的 RAW 跨度，补齐两种新建路径的差别。保持现有 Gate 行锁、Abort、投影分段。`RPC−脚本` 只能称为未解释残差，不能直接断言全部是网络或排队；Gate 行锁跨度也不改称纯等待。
4. **固定 60 对，仅 steady/replyExpanded，单次、单并发**。沿用既有 11563 评论、初始 1024 双侧占用、正常两进程 worker、真实 SESSION_CREATE/LIVE、原配额/1800秒TTL/预算、严格 TLS、TCP_NODELAY、计时前 0.27 秒节流和 seed20261025 的平衡块。30 对前后交换进程/IP；两半每来源各预热30次，120条预热不计入诊断。合计120条测量，不能根据结果增加样本、再跑一轮或改成其他路径。
5. 沿用既有时钟/资源预检及每项恢复要求；任何环境失败、HTTP 错误、脚本计时负值、时长无法闭合或记录缺失均记 `UNRESOLVED` 并停止，不重跑。仅在既有条件式系统修复授权仍适用时按原流程临时修复并恢复。此次审查没有启动环境或变更时钟。

判定只用全部固定样本，不筛选最快或尾部子集：扫描占比满足预设定义则假设获支持，下一候选优先减少扫描内重复解析/分配，并保留所有记录验证；未满足则假设被否定，不以此批准重写账本。另报客户端、脚本和 PG 写入的分布及与现有 Gate 跨度的关联，关联不等于因果。即使占比通过，也不能删扫描、缓存一次校验跨请求使用或宣告 3.62 ms 缺口已经解决；必须先给出具体等价改动再审查。若结果仍不足，明确剩余未知，不能自动增加诊断维度。

这次新增观测专门补现有证据缺口；**60 对诊断不产出新的产品 PASS/FAIL，不替换旧 300 对失败，不并入旧样本。**
