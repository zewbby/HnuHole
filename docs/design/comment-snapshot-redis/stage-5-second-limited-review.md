## 方案比较与推荐方向

| 方案 | 热路径及额外协议 | 当前裁决 |
| --- | --- | --- |
| 继续JSON微调/维护相位分散 | 可减少常数或周期碰撞，保留两次全表编码；无法消除已确认写成本 | 保留已验证优化，不凭此假定满足硬线。 |
| 全局计数+账号计数+分项Hash/索引，省略完整扫描 | 快，但需证明每个索引/计数部分丢失、部分写入和过期时不低估 | 不选；不能以可丢失的冗余计数取代完整名录重算。 |
| Hash分项写入但每次HGETALL完整验证 | 避免全表回写，但仍全量读取/解析；Redis7新Hash的建值与TTL不是单命令提交，需新建/恢复围栏 | 风险和实现面较大，不作为第一步。 |
| 分项发布状态/提交证书 | 可能省掉Publish的名录改写，但引入第二状态权威、GC与提交证书丢失协议 | 不选作首修；需要比现有协议更多证明。 |
| **定长二进制名录STRING，完整扫描，原子SET PXAT** | 去掉全局JSON解码/编码与逐项对象分配；只拼接字节段；保留原提交边界和命令集 | **优先评估的最小结构候选，须经独立测量再定案。** |

定长方案仍是O(N)校验、仍回写整个STRING，不能声称变成O(1)或必然通过5%。优势是保持一份状态权威和原有失败顺序，减小名录体积及JSON处理成本；如果独立测量不能支持充分收益，不能据推测扩大改造。

Hash并非不可行，但直接HDEL记录再更新头部会新增异常中间态：若后一步失败，剩余字段无法区分“已确认删除后正在核销”与“意外字段丢失”，需要额外journal、固定slot/tombstone或恢复协议。HSET也不是Redis7的新Hash创建+TTL的单命令边界。定长STRING继续复用已验证的原子保存和保守顺序，因而是本轮有测量支持、兼容风险更小的第一候选，而不是为了追求O(1)引入新状态权威。

Redis7的`SET ... PXAT`可一次设置值和绝对期限；HSET保留已有TTL，但不提供创建新Hash时的同一命令TTL，HSETEX自Redis8才提供。不能把脚本的原子可见性误当异常回滚，或假定客户端超时终止服务器脚本。依据：[SET](https://redis.io/docs/latest/commands/set/)、[EXPIRE](https://redis.io/docs/latest/commands/expire/)、[HSETEX](https://redis.io/docs/latest/commands/hsetex/)、[programmability](https://redis.io/docs/latest/develop/programmability/)。本设计继续使用Redis7，不为优化升级运行时。

## 定长候选格式（设计草案，不是产品实现）

独立新前缀`hnuhole:comment-snapshot:v2:<env>:`、新epoch、新运行ACL身份；control包含明确`ledgerFormat=2`，policy hash绑定格式标识和完整布局版本，不能与JSON版共用同一个control/ledger。仍是control、一个ledger STRING和不可变data STRING，不新增账号或nonce索引，不改变数据载荷MAC与游标V2格式。

头部68字节：magic/version 8、epoch原字节16、policy hash原字节32、until_ms uint64-BE 8、记录数uint32-BE 4。头部计数不作为预算权威；先检查总字节数、`len=68+206*count`、count上限及epoch/hash，再逐记录重算计数、总费用和所需账号统计。

每记录206字节，固定偏移如下（记录内1起始）：

| 字段 | 字节 |
| --- | ---: |
| snapshot UUID | 1–16 |
| owner用途摘要 | 17–48 |
| requestKey | 49–80 |
| requestScope | 81–112 |
| private attempt token | 113–144 |
| payload SHA256 | 145–176 |
| cost uint32-BE | 177–180 |
| created uint64-BE | 181–188 |
| expires uint64-BE | 189–196 |
| lease uint64-BE | 197–204 |
| flags / state | 205 / 206 |

所有定长摘要/令牌是原Base64/hex字段的原始32字节，不是省略验证。它们的合法二进制值域就是全部32字节序列；长度由布局和整值长度严格保证。Go私有操作信封提供相同原字节，Lua比较原字节；跨Go/Lua向量必须证明与原canonical编码一一对应，且UUID/owner/scope/token/digest与目标key和handle绑定正确。它不引入新的认证凭证或把用途密钥传给Redis。

uint64只接受0..2^53-1精确整数；解析先拒绝最高字节非0或次高字节>31，避免溢出后再比较。created>0，expires严格等于created+1800000且含宽限的until不超安全范围；lease继续在原允许范围内；cost检查原范围并按原记账公式产生；flags必须是合法Redis快照种类/排序，state只能PENDING/ACTIVE/ABORTING。全扫描检查重复ID和重复requestKey；任意目标命中也必须完成其余记录校验。只为目标保存解析视图，不为所有条目创建Lua对象。

编解码优先使用已有`struct`库，明确`>!1`为大端、1字节对齐及`I4/I8/B`固定宽度，不用依赖平台默认宽度或Lua5.3的string.pack。官方[Lua API](https://redis.io/docs/latest/develop/programmability/lua-api/#struct-library)列出了该库；对当前自有Redis7.0.15的两个无key、no-writes能力探针已确认：安全上界9007199254740991编码为`001fffffffffffff`并精确往返；头部/记录格式size为68/206；从指定偏移解码可用。该探针没有存储新格式或测量其性能。使用C库解包前仍须检查原始uint64高位，不能对已舍入的double补做上界判断。

8192项名录为1687620字节，保留原4MiB名录上限、12MiB固定预留、64MiB模块预算与所有调用期限；不以降低预留换性能。实际有效项数还受费用预算约束。新编码的Redis分配、Lua临时字符串/集合峰值必须实测，静态长度不是RSS证明。不可变data仍有原全量HMAC、归属、epoch、种类、排序、长度与ID数验证，正文继续原SQL/Gate实时校验。

## 原子状态协议与失败证明

所有扫描、判定和名录修改仍在同一个有界Lua脚本内，不能在Go下载旧名录、修改后无条件覆盖。Go只构造本次私有操作信封；头部与目标key、epoch、policy、ID和字段绑定须在脚本/共享编码向量中验证。

| 操作/不变量 | 定长候选必须保持的步骤与证明 |
| --- | --- |
| Prepare原子额度/预算 | 完整扫描重新计算全部费用、项数、当前owner占用及最早期限。再检查PG legacyCount、账号1024、模块64MiB、名录边界。先`SET ledger PXAT`追加PENDING，再推进control高水位，最后`SET data NX PXAT`。不同进程不能交错检查与写入；不信任可丢失的账号/总额缓存。 |
| 写入部分成功 | 保存名录前的构造/边界错误无持久修改；名录成功而control失败留下保守预留，不写data；control成功而data失败仍占额。不能因脚本报错逆向退额。 |
| SQL后Publish | 只在现有CommitAuthorized明确成功后调用。完整名录校验后匹配ID/owner/token/digest、有效PENDING租约及原载荷，拼接替换目标state字节，再单次`SET ledger PXAT`。仅确认ACTIVE或一次只读probe匹配ACTIVE后，服务才能签发游标。没有异步Publish或提前游标。 |
| 响应丢失幂等 | 同一Redis epoch/namespace的已ACTIVE requestKey返回原ID/flags/expiry，并重新授权、Load原MAC名单；不新增、不续期。PENDING仅同一handle可补完，其他尝试不接管；Publish重复是幂等ACTIVE。PG仍沿用原表协议，不虚构跨后端nonce事务。 |
| Abort与Publish竞争 | Abort先以同一脚本保存ABORTING，再DEL，最后release。Publish先赢则Abort返回ACTIVE且不得删；Abort先赢则Publish拒绝。失败保留原费用，不允许“检查pending后直接DEL”。 |
| release | 再完整校验最新名录；只删除仍为ABORTING/过租约/到期且对应data确认不存在的记录。压紧保留记录并单次保存，之后才能报告核销成功。并发两次release不重复减额；期间新Prepare记录保留。 |
| 崩溃 | 预留前无副作用；预留后/SQL前的PENDING按原租约回收；SQL已提交但未发布仍不发游标；ACTIVE响应丢失保留至固定期限并允许nonce恢复。 |
| 状态丢失/损坏 | control缺失/错类型/错hash/错格式拒绝；control水位仍未来而ledger缺失拒绝；长度/count/数字/重复ID或请求键等异常拒绝；不重建名单，不自动初始化、不静默PG降级。data缺失仍是该游标失效。 |
| 固定到期 | 数据的created/expires、成员和顺序不变；Publish/重试/Load只读或改变state，不改data。名录until取原值和control水位最大值，不延长数据TTL，空名录保留至原高水位。 |
| 读取权限与完整载荷 | Load仍只读小control+目标data，验证完整数据MAC和scope/ref，再走实时SQL内容权限。私有PENDING handle不可作为公开裸ID读取凭证。 |

二进制结构的“完整验证”与原JSON结构一样，是有界格式/字段/费用合计及数据载荷MAC验证，不宣称抵御持有Redis写权限者任意构造语义合法名录。新方案不能删掉现有校验；还须加入截断/整记录丢失与计数不符、重复ID、整数溢出、错误字段偏移、相同长度错误epoch/hash等负例。

## 60秒回收的边界与最小补强

现有6000项本机回收约百毫秒，证明该fixture的实际能力，不能推成所有受支持网络延迟下的上界。当前代码先串行DEL全部批次、再一次release；8192项按64分批为128次DEL，若每次接近100ms，单删除即12.8秒，超过5秒Collect总预算。超时后未释放前缀，下一轮重复前缀，不能据此证明健康60秒收敛。

候选补强仅用于Collect：对已确认到期或有ABORTING围栏的ID，以**最多8个且至少为前台保留一个池槽**的工作者并发执行原生DEL，`workers=min(8,poolSize-1)`，默认pool8为7。每条仍≤64 key，每个任务在真正取得工作者后才建立100ms调用期限。全组确认删除后才release；任何失败都保留未确认费用。Abort单份删除继续原调用/累计预算，不让请求级500ms预算因并发被重复花用。不能一次创建128个已开始计时、实际在池中排队的goroutine。

默认pool8、稳定时钟、每次含排队/网络的调用≤100ms、没有持续过载/失败的健康包络下，最坏128批为19波≤1.9秒，加due与release各≤0.1秒，合计≤2.1秒，留在5秒Collect内。PENDING在30秒到租约，最迟10秒后被选中，正常首轮约42.1秒完成；一次失败后下一健康轮约52.1秒，仍≤60秒。Runtime必须按配置检查`ceil(ceil(maxEntries/batchSize)/workers)*deadline + 2*deadline + 500ms调度余量 < 5s`；不满足的pool/batch/deadline组合不能作为格式2运行配置。内部小fixture仍可用Validate作竞态测试，但不能宣称其满足生产回收包络。当前默认8、batch64、deadline100不增加。

这是待Sol实施/验证的设计，不是已经修复的结果。新格式须重跑6000项及预算允许的最大最小载荷项数、真实租约、带受控网络延迟的默认pool8场景、DEL失败/超时和并发Publish/Abort；证明进度与无提前核销。后台相位只能在≤10秒tick包络内分散，不能靠降低维护频率换性能。

## 格式迁移、混跑和回退协议

本需求尚未提交、部署，JSON-R目前只存在于自有验收fixture。**首个正式部署优先从现有PG部署直接进入新前缀/新epoch**，不迁移或复用验收Redis。所有API先支持V1/V2 PG游标，新格式显式初始化、全部节点具备格式2读能力后才开启R创建；最后一个PG创建者停止后仍保留PG读满实际30分钟，再关闭旧表访问。

**新增P2发布桥接缺口：** HEAD基线`parseCommentCursor`只接受52字节V1；当前快照新建PG分支以`legacyCursor=false`进入尾部V2编码。若新节点已发V2而仍有旧节点接流量，正常PG翻页会被旧节点400拒绝。现有“新节点读V1/V2”测试没有证明旧节点可读V2。Sol须增加明确PG发出版本桥接控制：滚动期间新节点启用双读但仍发V1，确认全部接流量节点双读后才发V2/开启R；V1续页仍维持V1。反向二进制回退也先停发V2、等待最后V2 PG创建者的实际TTL窗口，再回只懂V1的节点。不得假定逐节点改配置天然是原子全量切流。该控制不能给PG性能基线添加无业务必要的Redis工作。

若未来确实已有活动JSON-R环境，采用有界排空，不做同一旧namespace原地换类型，也不同时启用两份独立R额度：

1. 在旧兼容版本明确切到PG创建、保留旧R读取和混合额度；所有节点确认后，operator将旧control置DRAINING。旧版Prepare已检查READY，因此不再接受新预留；已PENDING的SQL提交/Publish仍可完成，固定expires不变。记录高水位/最后创建者停止时刻。现CLI无drain操作，须增加受限显式operator入口，不能在runtime偷偷重置。
2. 保留旧R读者至其control最大水位（包括60秒宽限）过去，并通过旧协议Collect核实费用只剩固定预留、数据键已删。已有R初始nonce的恢复保证只在旧R协议内；如运营要求跨PG切换也必须恢复旧nonce，须先部署只读nonce恢复桥接版本，PG创建前优先恢复旧ACTIVE nonce，再排空；不得把这项语义默认为当前PG已支持。
3. 所有旧R均已失效且物理删除确认后，撤出旧R流量、使用PG-only配置滚动部署新格式API。旧/新API在此窗口只共同服务兼容PG游标。operator仅归档/清理自己旧前缀的空元数据，不使用FLUSH、不碰限流；旧费用/数据未清楚前不得初始化另一份活动R预算。
4. 以新前缀、新epoch、格式绑定policy和最小ACL显式初始化。所有可接流量节点必须确认格式2能力后才切换R创建。新旧脚本不得在同一namespace混写；旧程序指向新前缀会因配置/ACL/format-hash拒绝，不能解释新字节或写回JSON。格式2的兼容脚本小版本可各用自己的SHA和返回形状；更改布局或状态语义必须变更格式围栏。
5. 逻辑回退优先使用**仍能读格式2的同一兼容代码**切到PG创建、保留新R读和混合额度；不因Redis故障自动切换。若要二进制回到只懂JSON的旧版本，先对新R重复排空窗口，所有新R到期/删除后才用PG-only配置回退，旧配置须去掉不支持的新格式参数。不能立即把新R游标交给旧API。

该协议的代价是部署等待窗口和PG临时创建期，换取不引入跨两套R名录的原子配额转移。等待期间旧有效游标仍可读，数据到期不续期；它不是要求用户中途刷新。新格式激活时只存在一套可读R名录，PG/R额度仍沿用原SQL账号锁与Lua原子预留。无双活R就不需要把两份64MiB模块预算或两份1024额度叠加。

迁移期间必须区分操作围栏与可用性：格式/ACL/hash围栏能防止旧写入破坏新状态，不能替代“所有接流量节点已升级”的发布确认。若不能证明节点能力齐备，就继续PG-only，不开启新R创建。控制/名录丢失时停止该R创建并保留错误；恢复或等满旧水位后由operator显式换epoch，不在缺失状态上重置计数。
