**确认的夹具缺口。** `run.py`手工创建并封装TLS socket再直接赋给`conn.sock`，绕开本机Python标准`HTTPConnection.connect()`中设置`TCP_NODELAY=1`的步骤。静态遗漏已确认，约44–46ms残差与传输延迟相容，但没有做开关对照/抓包，**Nagle/延迟ACK因果尚未证实**；其对PG和R都存在，不能单独解释R回退方向。另有一个独立小缺口：compatibility续页中点重启后PG游标预热发送到PG进程，而正式比较把PG游标也发往R进程；这不解释回复预览/展开失败，但会污染续页预热对称性。

**最小修正方案，交由调度安排实施。**

1. 先修测量可解释性：手工TLS连接补齐标准客户端TCP_NODELAY设置，保留证书/SNI校验、每请求新连接及原计时起止；修正中点续页预热目标；在诊断开关下统一记录前置身份解析、Gate行锁、anchor写入、SQL提交、业务投影、Redis Prepare/Publish及HTTP完整耗时。只记录时长/分类/请求关联，不记Bearer、SQL参数或凭据。先用固定上限的传输开关对照验证44–46ms残差；若未消失就继续保留缺口，不能归因于网络。
2. 若仍需产品优化，优先审查空worker工作造成的共享Gate争用。可评估保守的只读候选预检/空批次退避或明确worker部署职责；所有实际业务动作和最终提交仍进入原Gate。预检结果只能决定暂不工作，不能授予权限、释放额度或绕过补偿；需证明不会超过清理/恢复上界。**不直接关闭生产worker、不把间隔从2秒改到60秒充当验收修复。**
3. 对前置限流身份解析的完整会话续期成本另做授权边界审查。不能直接删掉Gate、复用旧授权或把Prepare移出最终事务来省时间。现有证据不足以授权这种语义改动。
4. 当前不再盲改Lua。只有完整阶段计时确认Redis操作自身的尾部或队列占主要差异，才针对该点做最小优化，仍完整校验名录并保持SQL后发布与保守预算。
