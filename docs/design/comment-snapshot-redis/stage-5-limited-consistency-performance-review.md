## 瓶颈核实与归因限制

新建 Redis 快照必须经过 Prepare 和 SQL 提交后的 Publish。两次脚本都会解码并逐项校验全局名录，保存时重编码整份名录。冻结 `save(l)` 每次保存又执行两次 `cjson.encode`；因此一次正常新建有两次全局解码/校验，以及四次全局编码。PG 兼容模式只为混合账号额度调用一次 Redis Usage，随后写 PostgreSQL，不执行两次名录保存。回复预览正文较少，名录成本更容易显现。

只读 SLOWLOG 核查在名录约 809318 字节时捕获 126 个 write 脚本，耗时 12.814–19.467 ms，均值 14.868 ms。它与全局 JSON 写放大的机制一致。SLOWLOG 仅包含超过配置阈值的截断样本，不能拿该均值当作完整分布，也不能把 HTTP 尾延迟的全部差异都归给 Lua。HTTP 还包含 Safety Gate、SQL、进程调度和 I/O；当前 Store 指标为累计脚本耗时，尚无按 Prepare/Publish/Usage/Load 区分的完整分位数。

单次编码只降低常数成本和临时字符串峰值，**不改变名录操作随全局项数增长的 O(N) 特性**。不能推断它在更高占用或更多 API 实例下必然足够。

## 单次编码候选的安全等价性

候选先计算 `until_ms=max(l.until_ms,c.until_ms)`，必要时使用 `now+60000`，赋给本地 `l.until_ms`，再执行一次编码和最终字节检查，最后执行唯一的 `SET ledger ... PXAT until_ms`。

第一次编码确实具有提前发现序列化错误的作用，但原代码在第一次与第二次编码之间只改变本地表字段，没有 Redis 写入。当前 `l` 来源为已校验 JSON 或脚本创建的有界原生值；调用点没有 `pcall(save)` 后继续提交本地状态的路径。候选编码失败、分配失败或最终字节超限，仍在同一个持久化写入边界之前终止。本地 `until_ms` 的赋值不会被其他进程看到，不会留下外部部分写入。

真正保护名录字节预算的是**最终序列化产物**的长度检查；该检查仍在唯一 SET 之前。第一次检查不能替代它，删除第一次检查不允许最终超限产物写入。普通有效时间域内两次计算的最终内容相同；本结论针对预算、TTL、状态和故障不变量，不声明任意异常 JSON 输入的报错时刻逐字一致。

本轮逐项核对的不变量：

| 不变量 | 候选影响 |
| --- | --- |
| 全局 Lua 原子检查账号额度、总字节预算和名录项数 | 检查、计费公式、阈值均未移动或删除。 |
| Prepare 先保存预留，再推进 control 水位，最后写不可变数据 | 三个 Redis 写入的先后次序不变。 |
| SQL 最终授权事务提交成功后才 Publish，Publish 后才签发游标 | Go 调用顺序和所有错误分支不变。 |
| Publish 必须匹配 owner/token/digest、有效 pending 租约及原载荷 | 所有条件保留；只改变保存 active 名录的编码次数。 |
| Abort 先建立 ABORTING 围栏，再 DEL，最后 release | 流程不变；补偿失败仍保守占额，不能发布复活。 |
| Collect 只对到期或已围栏条目删除，确认数据不存在后释放 | 条件和操作顺序不变。 |
| 固定数据到期、名录最大到期加宽限及 control 水位 | 使用同一函数入口捕获的 now 和同样的 until_ms 算式；不续期数据。 |
| 缺失 control/名录时拒绝新建，旧游标不静默重建或退回 PG | 检查和错误映射不变。 |
| 原账号、帖子、楼层、排序、会话和实时正文权限 | 相关 Go 和载荷 MAC 代码没有变化。 |

因此，从当前代码控制流和持久化边界看，单次编码是可接受的最小候选；它的性能是否足够，必须由候选自身的完整对照判断。

## 给 Sol 的执行顺序与必要复验

1. 先保留单次最终编码这个最小差异，核对候选与待执行源码 SHA；不要顺带降低额度/预留、增加超时或删除完整性校验。候选四路径任一项超过 5% 仍为失败，不能挑另一轮通过值。
2. 先统一完整 fixture、名录占用、并发、预热、采样数量及后台维护配置，并增加每请求相对时间及固定 seed 的平衡请求顺序，避免与 1 秒 worker 或 10 秒维护周期发生固定相位偏差。保留所有样本和错误，分别诊断 Prepare/Publish/Usage/Load、Redis 排队与 SQL/Safety Gate；不得将重采样区间或均值替代 P95 硬线。
3. 真实 SQL 提交失败与 Safety Gate 冻结、Publish 回应丢失后的 probe、部分写入后补偿失败、32 并发配额、模块预算、OOM、状态丢失、6000 项清理、旧表停用和显式回退，都用最终源码重新验证受影响路径。真实 API + 真实 SQL 限流元数据 + 两个独立 Redis 的隔离不能用内存 Namespace fixture 替代。
4. 现有 HTTP 性能对照采用双读兼容模式，PG 也执行 Redis Usage。它证明的是该模式的比较，不能外推为停用旧表后的稳态性能；补列 PG-only 与 Redis-only 的同业务稳态对照，保留相同数据、TTL、账号额度和并发，不能给 PG 添加无业务必要的额外工作来满足比例。
5. 记录当前已完成的旧候选 30 分钟阅读和兼容窗口的版本。若后续改动改变到期、名录格式、发布/补偿或读写切换语义，必须重跑相应真实时间与跨版本验证；不能拼接成同一最终版本已全验。

单次编码现有证据尚不足。下一项可在不改持久化格式的前提下评估：让 `readLedger()` 一次完整校验同时返回已计算的总项数、总字节及所需账号统计，复用这些值；Collect 无待回收项时直接用该次校验的字节统计更新采样，不再另跑一次 Usage。回收有实际删除时，只在 release 成功后使用该次成功保存的统计。这样可减少 Prepare/Usage 的重复循环及每个副本每轮维护的重复全表解码，Go 公开 Collect 签名和持久化字段可以不变。

该后续优化仍须完整校验所有条目，不能提前遇到 nonce 就绕过剩余完整性检查，也不能以缓存统计替代原子预算。内部 Lua 响应形状变化必须配合各自脚本 SHA 的 Go 解码；旧/新进程可以继续各用自己的脚本，不能共享错误的返回值假设。若观测确认维护周期形成排队，再评估有上限的启动相位分散；它必须维持健康条件下 60 秒内回收目标，不能靠降低清理频率掩盖开销。本轮没有实施这些后续优化。

若仍不达标，单纯去掉校验、异步 Publish、先发游标后补账、提前释放预留，或忽略 ABORTING 都不可接受。应另作有版本围栏的名录/发布元数据设计审查，明确旧 GC 与新发布协议混跑、状态缺失和迁移窗口；不能在同一旧 namespace 下偷偷更换 Redis 数据类型。该结构性方案不在本轮实施范围。

性能 fixture 没有启用公共 SharedRateLimit 配置；另一组真实 API/SQL/双 Redis 的隔离用例启用了它，但不是性能采样。后续完整验收须明确对应哪套限流策略与运行配置，不能把“隔离用例通过”解释为全部 P95 已在实际启用限流的配置下通过，也不能为通过性能而削弱原有限流。
