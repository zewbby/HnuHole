## 环境与证明范围

脚本 [`tools/comment-snapshot-process`](../../../tools/comment-snapshot-process/README.md) 为本任务创建独占 PostgreSQL 16 私有 Unix socket 集群、Redis 7 子进程、正式 Goose 迁移、运行时最小权限以及独立的 `services/api/cmd/api` 命令进程。C Safety Gate 的证据、锚点、会话代次和最终 SQL 提交保持启用；不是同一进程注册两个 handler。

账号、身份、帖子及评论由一次性数据库预置，预置事务临时关闭触发器，随后恢复原触发器。全部测量请求通过真实 HTTPS、生产授权和 SQL/Redis 代码；**预置不能证明发布接口验收，主机链路不能冒充手机端到端或原生安全存储验收**。私钥、密码、bearer、数据库文件和 private 日志只在仓库外的私有运行目录。

主容量数据为 500 个主评论、每个 2 条回复，按每页 50 条读完 10 页，再逐一打开 500 个楼层回复。回复性能另用 1 个楼层、60 条回复，分别覆盖 5 条预览与 50 条展开。增长回归另外预置 10002 条主评论，单独记录总数据规模。

## 已验证的故障和容量边界

- 两个独立 API 进程交叉读取、复用同一初始 nonce、重启一个 API 后继续读取；同账号完成所需 501 个快照的阅读场景。
- 账号额度填至 1024 后，双进程 32 次并发请求全部被拒绝，并返回 Retry-After，没有超发。
- 真实 API 拒绝跨账号、篡改签名、主/回复游标串用和会话代次变化；载荷损坏返回完整性错误，数据丢失返回游标失效，名录丢失拒绝新建，实际断连和 Redis 重启没有自动初始化或静默退回 PostgreSQL。
- 实际 OOM 拒绝新快照，原不可变快照仍可读取。两个真实 API、真实 PostgreSQL 限流元数据和两个独立 Redis 进程证明：快照 OOM 不清除跨进程限流扣账，不重置限流代次；先前扣账仍使后续请求被拒绝。
- 实际 DEL 权限故障使补偿失败时，配额仍保守保留，ABORTING 状态不能重新发布。恢复权限后，6000 条乘增的 ABORTING 测试记录在单轮有界清理内回收；这是回收压力 fixture，不冒充 6000 次成功新建。
- 真实 Redis 暂停产生调用超时，符合调用和累计预算；受控时间验证到期前 1 毫秒可读、到期瞬间拒绝；另有实际 30 分钟测试，不能相互替代。

冻结正式容量场景结束时名录共 503 项（含两个既有测试快照），数据键合计 MEMORY USAGE 205080 字节，名录 229496 字节，保守预留 16752640 字节；账号填满后的 32 次并发新建均被拒绝。原始脱敏结果及版本在[审查机器证据](stage-5-limited-review-evidence.json)中单列，不作为本阶段整体通过。

## 发现及修复：增长后的初始 nonce

原服务先构造当前评论名单，再查询已有初始 nonce。原名单已成功发布后，评论总量增长超过 10000，会提前返回 `COMMENT_SNAPSHOT_TOO_LARGE`，妨碍同一 nonce 的重试。

当前修复只在当前名单超限时查询已提交的 nonce：匹配账号、帖子、楼层和排序后读取原不可变名单及原游标，不新增配额、不续期；没有原提交记录的新 nonce 仍返回 422。Safety Gate、会话和帖子权限先行校验，正文可见性和实时总评论数照常重查。常规未超限路径不增加额外 Redis 调用。

真实 HTTP 回归从 2 条增长至 10002 条：已复现修复前失败；修复后原 nonce 保持原成员和游标，新 nonce 仍超限，旧游标仍可翻页。实时 totalCount 可以更新，不要求整个响应字节不变。

## 默认参数与内存决定

维持 TTL 1800 秒、不续期；10000 ID；账号 1024 份；单份 196608 字节；模块保守预算 64 MiB，含 12 MiB 固定名录预留；名录最多 8192 项/4 MiB；Redis 调用 100 ms、累计操作 500 ms、池 8；pending 30 秒、清理间隔 10 秒、DEL 批次 64。

1024 可容纳两组完整的 501 份阅读快照并留 22 份余量；实际准入同时受全局预算约束。1 万 ID 的固定二进制载荷为 160153 字节，实测单键 MEMORY USAGE 约 164008 字节。在候选模块预算下，166 份最大名单保守预留 66977792 字节，第 167 份被容量拒绝；这不保证 501 份最大名单都能同时放入 64 MiB。

候选快照 Redis 保持独立进程、`maxmemory 128 MiB`、`noeviction`。原限流示例的 `maxmemory 256 MiB` 预算独立保留，不从限流实例分配快照内存。Redis allocator、Lua VM、连接及 RSS 还有额外开销；上线前须单独分配进程和宿主机内存余量，不能把 Redis maxmemory 当作操作系统进程硬上限。本阶段没有部署或验证生产 cgroup 配额。

## 性能判定方法和历史失败

首次对照的首次读取 P95 为 PG 446.738 ms、Redis 447.233 ms（+0.111%）；主评论翻页为 PG 392.361 ms、Redis 417.113 ms（+6.309%），**翻页未达到 5% 验收线**。该记录保留为失败，不能因其他功能通过而覆盖。

正式冻结批次使用固定源码，在本批次内保持相同数据、SQL、Safety Gate、配置与并发量 1；每种来源/路径预热 30 次，按请求对进行 AB/BA 交替，不删除慢样本。首次读取各 200 样本，主评论翻页各 1000 样本，回复预览/展开各 300 样本。翻页来源由签名游标决定，使用同一个 API 进程处理 PG 和 Redis 续页，排除“两个进程分别负责两种续页”的偏差；两种新建路径仍由相同二进制、只改变 createBackend 的进程处理。

正式冻结四路径 P95 回退分别为首次 +3.461%、主翻页 +2.955%、预览 **+5.317% FAIL**、展开 -0.444%；单次编码候选为首次 -2.731%、主翻页 **+6.174% FAIL**、预览 +4.258%、展开 -6.808%。两批均整体失败，不拼接不同版本的通过项。跨批次全库规模不同及抽样敏感性已在限定审查中说明，当前不能确定单次编码已足够。完整原始耗时保留，5% 硬线不变。

Store 操作另用 500 ID、530 项名录、30 次预热、500 次有效样本记录 Prepare+Publish 和 Load 耗时；该数字不含 SQL 或评论正文读取，不代替完整接口性能结论。
