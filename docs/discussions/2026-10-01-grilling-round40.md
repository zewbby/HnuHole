# 第四十轮：C/V 开发服务与目录闭环实施范围

日期：2026-10-01。四项必要决策已由用户逐项回答，本轮仅形成实施计划，不开展开发、下载或大型验证。

背景：用户名密码登录、完整会话、恢复／注销、凭据管理服务端与移动端核心链路已在隔离实验实现。真实 Flutter→C/V HTTPS／PostgreSQL 联调已完成部分验收；当前可启动服务仍是旧目录认证入口，正式迁移、持久任务装配及业务授权接 Gate 尚待实施。设备执行、完整 Android app、iOS Keychain 和生产安全验收仍有缺口。用户要求先规划，之后新开会话开发。

## Q1：V 的门禁是否同片实施

问题：本计划主线为可启动 C/V 开发服务、后台任务与通道目录接 C Safety Gate；V 的可信时间／旧快照冻结是否一起实现？

推荐：先完成服务与目录闭环，记录 V 安全边界；V 独立门禁另片，生产上线前必须完成。

用户答复：**“先服务／目录闭环，V 门禁另片（推荐）”。**

落实：本片盘点 V 的 DB 时间、OTP／预算、配额和收据恢复风险并明确开发限制，不把 C Gate 扩展声明为 V 的证明，不共享两方恢复信任。

## Q2：存量数据范围

问题：是否需处理另一电脑或其他环境中必须保留的既有账号数据？本 checkout 无本地数据库，不能由此判断其他环境。

推荐：全新开发库实施；旧通道升级仅在临时库验证；真实账号／未知库另写迁移操作包。

用户答复：**“全新开发库＋临时升级验证（推荐）”。**

落实：保留旧通道 UUID／code 的临时升级测试；旧演示会话不导入新认证。任何未知库与真实账号数据均不在本计划的操作范围内。

## Q3：开发入口兼容范围

问题：新会话的启动和验证应优先支持哪些 OS？现有 runner 依赖 POSIX sh／Unix socket，不能当作 Windows 原生命令。

推荐：Windows 与 macOS/Linux 均有明确步骤；Android／iOS 设备按实际环境分别登记。

用户答复：**“Windows 与 macOS/Linux 都支持（推荐）”。**

落实：Windows 支持方式由下一项依赖决策确定；平台未执行项如实记录，不用编译代替设备验收。

## Q4：Windows 服务端运行方式

问题：现有 Gate 锚点直接使用 Unix `syscall.Flock`，Windows 原生 Go 当前不兼容。是否接受 Windows Flutter／Android＋WSL2 Go／隔离验证＋Docker Compose 基础设施？原生 Go 会额外需要文件锁、原子替换及持久性适配。

推荐：WSL2，复用当前 Linux 文件锁与落盘实现。

用户答复：**“Windows 服务端使用 WSL2（推荐）”。**

落实：Go／Gate 文件／runner 在 WSL2 Linux 文件系统；Windows 宿主机可构建 Android。现有 Go headless mobile fixture 需要同平台 Linux Flutter，不接受直接塞入 Windows `.bat`。原生 Windows Go 适配不纳入本片。
