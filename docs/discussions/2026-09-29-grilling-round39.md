## Q1：FROZEN 时已有登录用户还能做什么？

场景：系统发现可信时间异常，或恢复了无法证明足够新鲜的数据库快照。数据库中某个 Bearer 看起来仍“未过期”，但现实中它可能早已过期或被替代。

**推荐：所有需要认证的社区读写都 fail closed。** 只保留无需账号的公开入口、健康检查和必要状态说明。

优点：不会在旧快照/不可信时间下继续把私有信息交给可能已经失效的 Session。  
代价：灾备门禁触发时，已登录用户也暂时无法访问本人私有数据。

备选：允许认证只读、禁止写/续期。体验较好，但安全边界更弱。

## Q2：谁可以解除 FROZEN？

**用户已明确：不需要双人控制。**

普通管理员、普通 API 实例仍不能直接点按钮解冻。正常生产恢复由单个受限恢复角色执行，并要求：

1. 新鲜独立恢复/时间证据；
2. 受限恢复权限；
3. 明确的恢复动作，推进 authorization_generation；
4. 审计记录。

若在线证据系统本身不可用，允许走受控 break-glass 灾备恢复，使用预先保管的离线恢复材料重新建立可信状态；仍不得直接绕过 Gate 强制 OPEN，也不要求两人共同审批。

隔离环境只用模拟的独立证据验证协议，不冒充生产运营设计。

## Q3：允许多少时钟回退不冻结？

**推荐：5 秒。**

≤5 秒：视为基础设施抖动，高水位不倒退，不触发全局冻结。  
>5 秒：进入 FROZEN。

这是工程参数，不是密码学常数；生产前可按真实授时环境重新校准。

## Q4：可信证据多久必须刷新？

**推荐：5 分钟。**

证据超过有效期后，不再产生或延长权限，进入安全不可授权状态。生产 TTL 最终根据真实证据服务 SLA 校准。
