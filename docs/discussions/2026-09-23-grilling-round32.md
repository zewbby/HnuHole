# 第三十二轮：邮箱—账号不可关联边界（已回答；实现边界待细化）

状态：2026-09-23。用户确认采用独立验证方与社区服务方的信任边界，并把现实身份不可识别从本轮邮箱隐私目标中分离。后续三项架构选择均按推荐确认。

## 已确认

- 本轮的核心承诺是“邮箱—账号不可关联”：平台内部任何单一人员、管理端或服务都不能取得某个具体验证邮箱与某个具体账号之间的对应关系。
- 邮箱验证码仍是唯一登录凭证；不增加密码，也不提供平台人工恢复入口。用户失去邮箱控制权时，平台不替其恢复账号。
- 邮箱验证方可以处理收件地址，但不能得到社区账号编号；社区服务可以处理匿名账号凭证和内容归属，但不能得到邮箱。
- 邮箱验证与社区服务需要由独立主体控制，不能由同一人员单独持有双方的密钥、日志和部署权限。
- “现实身份不可识别”是独立边界。本轮不把隐藏 IP、设备、时间、行为或内容推断纳入邮箱—账号不可关联的承诺。

## 现有规则的冲突

- 现有 `AUTH-LOOKUP-01` 仍描述由验证服务保存邮箱到账号的内部匹配标记；该方案不能直接作为最终实现。
- 同一邮箱回到原账号、七天注销期间重新登录撤销申请、以及注销后处罚连续，都需要某种稳定的机器匹配能力，但不能让任何单一服务得到邮箱与账号的完整对应关系。

## 架构选项的答复

1. 用户按推荐接受稳定匿名凭证；邮箱仍是唯一登录凭证，系统保留稳定匿名凭证到社区账号的映射，验证方不得获得社区账号映射。
2. 用户按推荐接受保证边界：任何单一主体不能关联；两个独立服务主动串通不在保证范围内。
3. 用户按推荐要求邮箱验证方与社区服务方由不同组织或法律主体控制，不能由同一组织权限隔离替代。

## 已形成的架构决策

- 新增 [ADR 0005：隐私认证与邮箱—账号不可关联](../adr/0005-privacy-preserving-email-authentication.md)，状态为 accepted；协议的具体算法和参数尚未选定，也尚未实现或安全评审。
- 账号模块 AUTH-LOOKUP-01 已由验证服务保存邮箱匹配标记，改为跨组织隐私协议产生稳定匿名凭证；候选包括盲签名、门限 OPRF 或经安全评审的等效协议。不能以普通无密钥邮箱哈希、单方 HMAC 或可解密邮箱副本代替。
- 跨服务不得共享请求编号、幂等键、精确时间关联日志、备份或密钥；跨方请求和故障恢复协议待设计。
- 用户失去邮箱控制权时无人工恢复入口；验证服务不可用时失败重试，不回退到管理员查邮箱或人工关联。

## 后续确认与实现待细化

- 稳定匿名凭证是否由用户设备持有，或只作为每次邮箱验证后取得的协议产物；设备重装后仍通过邮箱恢复，但平台不能提供绕过验证的恢复。
- 正式注销后，既要允许同邮箱创建全新账号，又要让尚未到期处罚继续生效；需要定义仅社区侧可判定且不把旧账号直接暴露给用户的处罚连续凭证。
- 验证码申请对新旧邮箱统一返回受理状态和通用提示已确认，见[第三十五轮](2026-09-23-grilling-round35.md)；响应时延、限流和实际投递路径的侧信道量化验收仍待安全评审。
