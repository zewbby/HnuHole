# 第三十八轮：恶意验证方与认证架构升级（转 Codex / GPT-6 决策）

状态：2026-09-26。**本轮未形成最终认证方案。用户决定把架构决策交给 Codex 中的 GPT-6。**

## 触发问题

在继续评估 ADR 0005 时，用户提出：如果邮箱验证方不是“诚实但好奇”，而是主动恶意伪造“验证码已验证成功”，现有“邮箱验证码直接恢复/决定社区账号”的思路是否会导致账号接管和邮箱—账号关联泄漏。

讨论确认：OPRF、VOPRF、盲签名等原语可以改善输入/输出隐私和凭证关联性，但不能凭空证明“邮箱验证方没有对邮箱控制权撒谎”。如果唯一验证方同时掌握“是否验证成功”的最终判断权，而邮箱验证码又是恢复已有账号的唯一根凭证，则完全恶意验证方属于实质性的账号接管风险。

## 用户对双验证方案的反馈

曾讨论两个独立邮箱验证方、2-of-2 验证或门限方案，以抵抗任意一个验证方主动恶意。但这很可能要求两次独立邮箱控制权证明（例如两个验证码），用户明确指出 Hnuhole 是 To C 产品，长期或常规出现双验证码体验不可接受，除非确实没有更合理方案。

因此没有把“双验证码”写成最终规则。

## 新候选方向

提出把两个问题分离：

1. **校园资格**：证明“我是合法校园用户”。
2. **账号控制权**：证明“这个 Hnuhole 账号由我控制”。

候选思路：
- 校园邮箱 / 学校 SSO 只用于取得匿名校园资格凭证；
- 使用盲签名、Privacy Pass 类 token、匿名凭证、BBS+、VOPRF 或其他成熟标准把资格证明与社区账号隔离；
- Hnuhole 账号本身绑定 Passkey / WebAuthn / 用户侧密钥；
- 后续账号登录主要靠 Passkey，而不是再次让邮箱验证方决定已有账号归属；
- 如果验证方恶意，它可能仍能伪造“新资格”，但不能仅凭验证权限接管已有 Passkey 账号；
- 最大未决问题变成：Passkey 丢失和全部设备丢失后的账号恢复，恢复流程不能退化成“单邮箱验证码即可重置已有账号”，否则恶意验证方风险重新出现。

## 本轮没有确认的事项

以下全部仍待 GPT-6 架构评审，不得误写成已确认：
- 是否正式引入 Passkey / WebAuthn；
- 是否推翻“邮箱验证码是唯一登录凭证”；
- 是否继续使用稳定匿名标识；
- 是否使用盲签名、VOPRF、门限 OPRF、Privacy Pass、BBS+、ZK Email；
- 是否接入学校官方 SSO；
- 是否需要两个邮箱验证方；
- 最终账号恢复模型；
- 最终生产信任主体数量。

## 已确认继续有效

- 用户要求强匿名，而不是仅“不在业务表里存邮箱”。
- 用户不接受单个验证方主动恶意即可轻易接管已有账号却仍被宣传为“强保护”。
- 用户是 To C 产品，不能只追求理论安全而忽略登录与恢复体验。
- 正式注销后创建新账号，旧禁言不延续；封禁期间不可注销。
- Hnuhole 作用域匿名标识和密钥轮换不改变逻辑主体的约束，如最终架构仍存在稳定 pseudonym，则继续适用。
